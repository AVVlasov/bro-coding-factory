## Приоритет 0 — надёжность ядра

### 1. CI и один скрипт запуска всех сюит

.github отсутствует, четыре набора тестов запускаются руками четырьмя командами. Сюиты уже офлайн-безопасны (фейковый агент, чистый git, скип без docker), так что GitHub Actions с одним скриптом закрывает дыру за час. После этого каждая следующая правка получает доказательство, а не надежду.

### 2. Единый рантайм вместо копий

Собрать общее в harness/lib/runtime.ps1: Log (четыре копии с разными цветовыми схемами), Verdict-Pass (loop.ps1:165 и run-all.ps1:63, сигнатуры уже разошлись), парсер ответа судьи (три схемы в m13-bridge.ps1:464, loop.ps1:1267, verify.ps1:1166), UTF-8 блок (10 файлов), append событий под мьютексом. Конкретные жертвы размножения, все проверено:

| Что | Копия 1 | Копия 2 | Следствие |
|---|---|---|---|
| Гард конкуренции verify читает мёртвый журнал | event-bus пишет в .bcf/events.jsonl | verify.ps1:314 читает harness/events.jsonl | защита от двойного прогона не видит реальной активности |
| Heartbeat-фикс от 26 мая | verify.ps1:141-147, постоянный handle | loop.ps1:682,750, open на каждый тик, пустой catch | потеря дельты stdout даёт ложные stall-kill'ы |
| Regex деградировавших тестов | loop.ps1:193,212 | verify.ps1:676 | правка в одном месте расходится со вторым |
| Вердикт PASS/FAIL | loop.ps1:165 | run-all.ps1:63 | критерий приёмки существует в двух версиях |

Комментарий в loop.ps1:1254 сам фиксирует, что расхождение парсеров судьи стоило 11 итераций. Этот класс ошибок лечится только одним модулем.

### 3. Гейты fail-open

Проверено: в loop.ps1:856 вызов npx без проверки доступности — при отсутствии npx берётся протухший $LASTEXITCODE от предыдущей команды git, и регрессия типов молча проходит. lint-gate реагирует только на exit 1, упавший скрипт неотличим от найденных нарушений. Гейт, который не смог выполниться, должен проваливать задачу явно, а не выглядеть как пройденный.

## Приоритет 1 — честность CLI

Все позиции проверено чтением:

| Где | Что происходит |
|---|---|
| run.ps1:47 | `bcf run --budget` последним аргументом даёт [double]$null = 0, ноль означает «без лимита». Предохранитель денег отключается молча |
| update.ps1:62 | провал git fetch проглатывается, офлайн сравнение идёт с устаревшим upstream и печатает «новее нет» |
| stop.ps1:73 | Get-CimInstance Win32_Process существует только на Windows, на Unix аварийный тормоз отчитается «снимать нечего» при живых агентах |
| backends.ps1:270 | пробы авторизации doctor без таймаута, зависший CLI вешает doctor навсегда |
| pricing.ps1:44 | поиск тарифа подстрокой, первый совпавший: gpt-4o посчитается по тарифу gpt-4o-mini или наоборот в зависимости от порядка ключей |

Отдельная развилка: пути состояния собираются с `\` внутри сегментов (paths.ps1:57 `.bcf\project.json` и ещё около двадцати мест по src/ и harness/). На Linux это легальное имя файла с обратным слэшем, слой состояния там не работает, хотя sh-обёртка bin/bcf и не-Windows ветка setup написаны. Либо чинить слой путей через платформенный разделитель в одном модуле, либо честно объявить в README требование Windows. Тянуть двусмысленность нельзя: обёртки обещают то, что состояние не выдержит.

## Приоритет 2 — чистота и масштаб

- Бизнес чужого продукта в движке. Проверено: loop.ps1:566-569 хардкодит маппинг stack→ScreenServices, pulse→ScreenPulse из task-scope конкретного приложения. Для любого другого проекта маппинг молча пуст и механизм reference-digest не работает вовсе. Место этому в config/scope-map.json проекта, канал уже есть. Там же triggers.ps1:59 читает config/triggers.json из корня фабрики, а не проекта: все проекты делят один список триггеров, проектный игнорируется.
- Мёртвый код. Invoke-ClaudeCode (verify.ps1, единственное упоминание — определение), Get-LastVerdict и Count-ConsecutiveFails (event-bus), Read-BcfChoice и Read-BcfText (ui.ps1), Get-BcfGraphRoot (journal.ps1). Удалить.
- Две реализации живой доски: watch.ps1:40-184 против lib/runview.ps1:115-250, уже разъехались возможностями (ETA есть в одной). Оставить одну.
- Разбор позиционного аргумента скопирован дословно восемь раз (cost, report, board, watch, meta, memory, task, research).
- Масштаб. Compute-State перечитывает весь events.jsonl каждую итерацию (event-bus.ps1:112-156), watch раз в секунду перепарсивает журналы всех прошлых прогонов. На сотне задач и сотне прогонов линейно замедлится именно там, где долгая работа.
- Со слов разбора (код видел, сценарий не воспроизводил): watchdog планировщика может упасть на несуществующем ключе Started (scheduler.ps1:159); откат красного слияния делает reset --hard HEAD~1 на общем дереве и способен стереть посторонний коммит, попавший в окно между merge и проверкой (scheduler.ps1:256).

## Покрытие тестами, самые опасные дыры

Карта собрана grep-ом absence-проверками:

1. Команды memory, research, prd — ни одного теста. setup и update прикрыты только флагом --check, сама установка в PATH и само обновление не тестируются.
2. pricing: позитивная ветка расчёта денег не покрыта, проверены только случаи «тарифа нет». Неверная цена напечатает правдоподобное число, а это ровно тот класс «отчёт соврал», который сюита ловит везде, кроме здесь.
3. run-all, fanout, scheduler — оркестрация волны решает, какие задачи поедут, без единого упоминания в тестах.
4. claims: конкурентный допуск двух агентов на одну задачу не воспроизводится ни разу.
5. Одиннадцать модулей harness/lib вне поля зрения: evidence, hard-cap, harness-guard, bug-supervisor, reference-digest, vision-baseline, visual-context, redo-trigger, оба адаптера opencode.

## Контекст рынка, коротко

Изоляция worktree, доски параллельных агентов и арбитраж слияний стали в 2026 стандартом категории (Conductor, Vibe Kanban, Claude Squad, встроенные Agent Teams Claude Code, Codex multi-agent v2). Ниша фабрики — ночные автономные прогоны с детерминированной приёмкой и памятью ошибок — конкурентами закрыта слабо, там у всех интерактивные сессии человека с агентом. Но преимущество держится на одном обещании: вердикту можно верить. Гейты fail-open и непроверяемый движок вердиктов бьют именно по нему, поэтому приоритет 0 про честность, а не про новые функции.

## Развилки

- Кроссплатформенность: чинить слой путей или объявить Windows-only в README?
- runtime.ps1: делать единый модуль сейчас или ждать второго случая? Моя ставка: сейчас, класс «фикс не доехал до второй копии» уже стрелял дважды.
- CI: GitHub Actions или локальный скрипт pre-push? Ставка: Actions, машина не должна быть обязательной для проверки чужого вклада.

Порядок работы предлагаю такой: CI, единый рантайм, fail-open гейты, честность CLI, потом чистота. Первые три пункта — примерно день работы и снимают весь класс молчаливых поломок.
