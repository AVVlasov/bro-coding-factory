# Справочник конфигурации

Всё проектное живёт в `config/` **внутри проекта**. Скрипты читают отсюда и не хардкодят
ничего. Секретов здесь нет: ключи берутся из окружения.

Аргументы командной строки перекрывают конфиг, конфиг перекрывает умолчание скрипта.

---

## config/harness.json

| Ключ | Что это |
|---|---|
| `engine` | Косметическое имя движка (по умолчанию `ralph`). |
| `repo` | Имя репозитория для общей памяти команды: под ним заметки лежат снаружи, по нему их находит хук перед задачей. Пусто = имя каталога проекта. |
| `agent.command` | Команда бэкенда для ЦИКЛА. `{model}` подставляется, промпт идёт на stdin. |
| `agent.adapter` | Разборщик потока из `harness/lib/adapters/`. |
| `models.code` / `.tester` / `.vision` / `.judge` | Модели цикла. Пусто = умолчание бэкенда. |
| `graph.backends.<имя>` | `{ command, format, env, probeModel, authCheck, authOkPattern }`. Заполняет `bcf init` по результатам опроса установленных CLI. |
| `graph.roles.<роль>` | `{ backend, model, fallback }` для `planner` / `arbiter` / `critic` / `worker` (и опционально `researcher`). `fallback` — запасная модель, см. ниже. |
| `paths.*` | Где живут задачи, вердикты, текущий фокус, баги. |
| `productPaths` | Что считается продуктовым кодом. |
| `generatedFiles` | Файлы, воспроизводимые сборкой. |
| `taskIdPattern` / `taskIdPrefix` | Формат id задач (умолчание `[A-Za-z][A-Za-z0-9]*-\d+`, префикс `TASK`). |
| `backpressure.typecheck` | Быстрые проверки после каждой итерации, массив команд для любого стека. Пустой массив = пропустить. |
| `tests.*` | `runner` (cargo/vitest/jest/pytest/go/maven/custom) плюс переопределения `command`, `packageFlag`, `passedPattern`, `failedPattern`. |
| `net.probeHost` / `.probePort` | Сторож соединения (хост API модели). **Пусто = выключен.** |
| `timeouts.*` | `iterSec`, `streamStallSec`, `netWaitMaxSec`, `netStallRetryMax`, `stepSec`, `silentSec`, `testerSilentSec`. |
| `limits.*` | `taskConcurrency`, `agentConcurrency`, `fanoutConcurrency`, `testerConcurrency`, `maxIterations`, `noProgressLimit`, `sprawlFileLimit`, `sprawlIterLimit`. |
| `judge.name` / `.outputSuffix` | Имя роли судьи и суффикс его файла вывода. |
| `features.*` | `memory`, `bugSupervisor`, `hardCap`, `fanout`, `vision`, `visualContext`, `referenceDigest`, `redoTrigger`. По умолчанию всё выключено. |
| `envPrefix` | Префикс переменных окружения (по умолчанию `BCF`). |

### Четыре ключа, ошибка в которых стоит дороже прочих

**`productPaths`** решает, где искать «прогресса нет» и расползание скоупа, и что вообще
смотрит ревью. Ошибка здесь означает, что правки в доках засчитываются как работа над
задачей — а цикл при этом честно докладывает о прогрессе.

**`backpressure.typecheck`** вызывается КАЖДУЮ итерацию: цикл исполняет этот массив как
есть и сам ничего не знает ни про `npx`, ни про `mvnw`. Для TypeScript это
`npx --no-install tsc --noEmit`, для Maven — `.\mvnw.cmd -B -q -o -DskipTests test-compile`
(именно `test-compile`, иначе сломанный тестовый исходник доедет до верификации и сожжёт
круг). Команда, которой не существует, делает гейт красным всегда, и агент начинает чинить
несуществующее. Поэтому `bcf init` запускает кандидатов живьём и записывает только те, что
отработали.

Пустой массив — законное состояние, но означает он «не проверялось», а не «чисто»: цикл
записывает событие `backpressure-skipped`, чтобы пропуск было видно в журнале.

**`generatedFiles`** — что не блокирует слияние. Один изменённый лок-файл в основном
дереве однажды завалил слияние семи задач подряд, каждая из которых уже дошла до PASS:
весь бюджет прогона сгорел из-за файла, который сборка перегенерирует за секунду.

**`tests.runner`** — чем доказывается закрытая задача. Пока он пуст, гейт «фича доказана
тестами» не работает: общий прогон тестов зелен и на пустом месте.

### Про роли графа

Три правила, которые `bcf init` не даёт нарушить молча:

1. `critic` не сидит на модели `worker` — несколько агентов одной модели на одном
   контексте приходят к одной ошибке и подтверждают её друг другу;
2. `planner` и `critic` из разных семейств — критик не защищает решение своего
   планировщика;
3. роль, обязанная только смотреть, живёт на бэкенде с песочницей «только чтение».

Ещё одно свойство, о котором стоит знать: у части бэкендов (`cursor`, `gemini`, `aider`)
в потоке НЕТ события о расходе токенов. Узлы такой роли для бюджета нулевые, и потолок
«до исчерпания» на ней не сработает никогда. `bcf doctor` и `bcf cost` называют это явно.


### Запасная модель роли

```json
"arbiter": { "backend": "claude", "model": "opus", "fallback": "sonnet" },
"critic":  { "backend": "cursor", "model": "grok-4.5-high",
             "fallback": { "backend": "codex-ro", "model": "gpt-5.6" } }
```

Строка означает «та же CLI, другая модель»; объект — другую CLI целиком.

Включается ОДИН раз на узел и только когда отказал **провайдер**, а не задача: 429 или
исчерпанный лимит плана, зависший и снятый по тишине поток, отвалившаяся на ходу
авторизация, пустой ответ при нулевом коде. На «ответ не прошёл схему» и «проверки
красные» НЕ включается: вторая модель упадёт на том же, а бюджет спишется дважды.

Без запасной узел падает, волна встаёт и ждёт рук. На слиянии это дороже всего: рабочее
дерево остаётся заклеймлённым, и следующие задачи не берут те же файлы.

Переключение пишется в журнал событием `node-fallback` — по нему видно, что прогон ехал
не на той модели, которую выбирали.

## config/agents.json

Роль → `{ file, model }`; `testers` — массив `{ name, file, model }`. Пустая `model`
наследует `models.*` из `harness.json`. Файлы ролей лежат в `.claude/agents/` — одно
место и для Claude Code, и для верификации.

## config/checks.json

Обязательные детерминированные проверки — **авторитетный источник вердикта**. Ключ = id
задачи или `_default`, значение = массив shell-команд (exit 0 = зелено).

Их пишет владелец, а не агент: verify объединяет их с планом из `VERIFY-REQUEST`, и убрать
их агент не может. Это и закрывает дыру «агент пишет себе план и получает тривиальный
PASS».

Пустой `_default` — это не «нет проверок», а «задача без собственных проверок может
получить PASS на одном судье».

## config/triggers.json

Триггеры трения: на чём цикл обязан остановиться и позвать человека.
`bigDeletionThreshold` (строк) и `pathTriggers[]` из `{ pattern, reason, severity }`,
сопоставляемых с диффом итерации.

## config/scope-map.json

- `testers[]` — `{ tester, patterns }`: какой тестер относится к каким путям. Тестеры, не
  относящиеся к диффу, из плана верификации выбрасываются — тестер на чужой поверхности
  докладывает «чисто» бесплатно.
- `vision.rules[]` и `vision.shared.patterns` — скоуп визуальной фазы.

Сравнение подстрочное, а не по маске: `**` здесь ничего не делает, а короткий префикс
захватывает лишнее. В раскладке Maven `src/` покрывает заодно `src/test/java` и
`src/main/resources` — архитектурный тестер начинает вызываться каждую итерацию, а `api`
и `performance` не совпадают никогда.

## config/journeys.json

Реестр сквозных сценариев: чем доказывается, что продуктом можно пользоваться.

| Ключ | Что задаёт |
|---|---|
| `command` | Чем прогоняются все сценарии. Пусто = `tests.command` из `harness.json`. |
| `commandOne` | Чем прогоняется ОДИН сценарий; `{id}` подставляется. |
| `journeys[].id` | Обязан дословно встречаться в выводе прогона. |
| `journeys[].proof` | Файл, который сценарий доказывает. |
| `journeys[].status` | `required` (умолчание) или `planned`. |

`commandOne` обязателен для всего, кроме vitest и jest. Гейт добирает им поштучную
атрибуцию — «какой именно путь красный»; фолбэк, который он собирал раньше, добавлял к
общей команде флаг `-t <id>`, а этот флаг понимают только vitest и jest. Maven, pytest,
cargo и go падают на нём разбором аргументов, и гейт называл это «сквозной путь сломан» —
проект шёл чинить продукт вместо конфига. Теперь гейт отказывается вслух. Для Maven это
`.\mvnw.cmd -B verify -Dit.test={id}` (failsafe) или `-Dtest={id}` (surefire).

## config/review-lenses.json (опционально)

Ракурсы для `bcf run review` — массив `{ key, ask }`. Дефолт намеренно общий
(корректность, отказы, границы, честность тестов): он ловит то, что ломается в любом коде,
и не притворяется, что знает предметную область. Проект, у которого есть свои характерные
классы дефектов, переопределяет их здесь.

## config/pricing.json (опционально)

Тарифы для `bcf cost`, цена за 1M токенов:

```json
{ "updated": "2026-07-31", "currency": "USD", "rate": 1.0,
  "models": { "opus": { "input": 15, "output": 75 } } }
```

`updated` печатается вместе с суммой: прайсы меняются, а файл — нет. Модель без тарифа
показывается прочерком, а не нулём.

Если файла нет в проекте, берётся `memory/pricing.json` фабрики.

## config/memory.config.json

Подключение к pgvector и эмбеддинги: `host`, `port`, `database`, `user`, `password_env`,
`password_default` (несекретный локальный фолбэк), `project`, `schema`,
`embedding_dim` / `_model` / `_endpoint`, `connect_timeout_sec`.

Порядок поиска: `BCF_MEM_CONFIG` → `<project>/config/memory.config.json` →
`<factory>/memory/memory.config.json`, а поверх найденного — накладка машины
`.bcf/memory.local.json`. Одна установка pgvector обслуживает много проектов, поэтому
фабричный конфиг — база, а проектный только переопределяет его.

**`host`** — адрес сервера базы. `localhost` (умолчание) означает контейнер на этой же
машине: тогда `bcf memory init` его и поднимает. Любой другой адрес означает базу на
другой машине — контейнер не поднимается, `bcf memory down` ничего не останавливает, а
пароль по умолчанию перестаёт быть допустимым (см. ниже).

**`password_default`** годится ровно для локального контейнера: он лежит в открытом
репозитории и секретом не является. На сетевом адресе `bcf memory init` откажется
работать, а `bcf doctor` покажет это блокирующей проблемой — задай настоящий пароль в
переменной из `password_env` (по умолчанию `BCF_PG_PASSWORD`).

**`project`** — чьи записи уходят в общую базу. Пусто = имя каталога проекта;
`BCF_MEMORY_PROJECT` сильнее конфига. Отзыв спрашивает сначала свой проект и добирает
чужое, только если своего не хватило до `k`: похожесть считается по тексту и границ
проекта не знает, поэтому без этого поля агенту на Java прилетает урок про Electron.

`embedding_dim` ОБЯЗАН совпадать с моделью (bge-m3 = 1024): иначе база отвергает записи,
и выглядит это как «память пустая».

Схему применяет `bcf memory init` (`python memory/pgvector/memory_client.py migrate`).
Сам контейнер выполняет `init.sql` только при первой инициализации пустого каталога
данных — базе, поднятой раньше, новые колонки иначе не достанутся никогда.

## .bcf/memory.local.json

Накладка ЭТОЙ машины: `port` и `container`. В git не попадает (`.bcf/` в `.gitignore`).

Порт 5433 записан умолчанием во все установки фабрики, поэтому вторая установка или
соседний проект приходят в занятый порт. `bcf memory init` подбирает свободный и пишет
его сюда. Пока он писался в `config/memory.config.json`, у владельца появлялся дифф,
которого он не делал, а коммит увозил номер порта его машины всей команде.

## .claude/hooks/hooks-config.json

Проектные проверки гейтов, все no-op пока не заполнены:

| Ключ | Что включает |
|---|---|
| `ipc_dirs`, `ipc_preload_file`, `ipc_types_file` | Проверка тройной проводки канала: зарегистрирован, есть в мосте, есть в типизированном клиенте. Канал, проведённый в одном месте из трёх, компилируется и падает только в рантайме. |
| `migration_*` | Регистрация миграций и безопасность `ALTER`. |
| `wrapper_allowed`, `wrapper_key_pattern` | Гейт «в код не добавили литерал ключа API». |
| `console_check_dirs`, `banned_ui_patterns` | Правила lint-gate. |
| `ts_targets`, `py_targets`, `java_targets` | Какие расширения гейт считает кодом. `.java` включает ветку `mvn test-compile` при наличии `pom.xml`. |
| `config_targets` | Ресурсы и конфиги, которые проверяются на ключи API наравне с кодом: ключ в `application.yml` утекает так же, как ключ в константе. |
| `bare_catch_targets` | Где ищется пустой `catch`. По умолчанию TypeScript и Java. |
| `test_paths` | Где лежат тесты, если они снаружи `productPaths`. Пусто при наличии `pom.xml` = стандартная раскладка Maven. |
| `product_paths` | Каталоги, которые сканирует детектор посторонних алфавитов в UI-строках и детектор моков в продуктовом коде. |
| `mock_scan_ext` | Расширения, в которых ищутся моки и заглушки внутри `product_paths`. |
| `renderer_dir`, `renderer_forbidden_import` | Запрет пересечения архитектурной границы импортом. |

## Переменные окружения

Полный список — `.env.example` в корне фабрики: там перечислено ВСЁ, что читает обвязка,
именами и без значений. Пример со значением копируется в `.env` целиком и становится
настройкой, которую никто не выбирал, поэтому значений там нет ни одного. Полноту файла
проверяет `tests/memory-team.tests.ps1`: он собирает имена из исходников и сверяет с
образцом в обе стороны.

Ключевые:

| | |
|---|---|
| `BCF_PROJECT_ROOT` | над каким проектом работает движок. Выставляет `bcf`; вручную нужен только при прямом запуске скриптов харнесса. |
| `BCF_HOME` | корень фабрики. |
| `BCF_API_KEY` | ключ для ролей, которые ходят к модели напрямую (ретроспектор, супервизор, автор тестов). Без него их вызовы возвращают отказ авторизации, а выглядит это как «субагент ничего не нашёл». |
| `BCF_PG_PASSWORD` | пароль pgvector. Обязателен, когда база не на этой машине. |
| `BCF_MEM_CONFIG` | явный путь к конфигу памяти. |
| `BCF_MEMORY_PROJECT` | под каким именем этот проект пишет в общую базу памяти. |
| `BCF_MEMORY_DISABLED=1` | выключить память для одного прогона. |
| `BCF_FLEET_DIR` | где лежит общий реестр агентских слотов (по умолчанию `<фабрика>/.bcf/fleet`). |
| `EOG_BIN` | путь к `eog`, если его нет в PATH: хук перед задачей дописывает заметки общей памяти команды. |
| `BCF_NO_COLOR=1` | вывод без цвета. |
| `BCF_VISION_*` | команды визуальной фазы. |

Секреты не коммитятся: ключи живут только в `.env` (в `.gitignore`). `bcf doctor` читает
и окружение, и `.env` проекта — ровно оттуда же, откуда их возьмут сами вызывающие
скрипты, — и называет роли, которым ключа не досталось.
