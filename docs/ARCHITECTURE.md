# Устройство

## Два корня, и путать их дорого

| | что это | где живёт |
|---|---|---|
| **фабрика** (`BCF_HOME`) | движок, шаблоны, мета-слой, память | одна установка на машину |
| **проект** (`BCF_PROJECT_ROOT`) | код, `config/`, `tasks/`, `.claude/`, `.bcf/` | сколько угодно |

Движок в проект не копируется. `bcf` резолвит корень проекта один раз — из `--project`,
иначе из `BCF_PROJECT_ROOT`, иначе из верха git-репозитория — и передаёт дальше
переменной окружения. Всё состояние прогонов пишется в `<project>/.bcf/` и целиком
принадлежит проекту.

Ошибка в этом месте молчалива и стоит дорого: клиент памяти, который ищется в проекте,
не находится — и память просто отключается на всех проектах, кроме самой фабрики. Поэтому
`harness/lib/bcf-context.ps1` разводит `Get-BcfProjectRoot` и `Get-BcfHomeRoot`, и каждый
путь использует свой. Проект узнаёт корень фабрики из карточки `.bcf/project.json`
(поле `bcfHome`, её пишет `bcf init`) — по ней же его находят хуки, у которых нет ни
переменных окружения `bcf`, ни права на абсолютные пути.

### Что общее на установку, а что принадлежит проекту

| Общее (фабрика) | Почему не по проектам |
|---|---|
| база памяти pgvector | одна установка на машину; чей опыт, говорит поле `project` в каждой записи |
| реестр агентских слотов (`<фабрика>/.bcf/fleet`, `BCF_FLEET_DIR`) | потолок упирается в rate-limit провайдера, а он общий: два проекта с потолком 6 запускали двенадцать агентов, и провайдер отвечал отказами всем сразу |

| Принадлежит проекту | Что там |
|---|---|
| `config/` | решения владельца, лежат в git и одинаковы у всей команды |
| `.bcf/` | состояние прогонов, карточка проекта, накладка машины `memory.local.json` (подобранный порт и имя контейнера); в git не попадает |

Разделение не косметическое. Порт памяти писался в `config/memory.config.json`, и
у владельца появлялся дифф, которого он не делал: коммит увозил номер порта его машины
всей команде. Адрес сервера — решение проекта и остаётся в `config/`; порт — свойство
машины и живёт в `.bcf/`.

```
bin/bcf.ps1          диспетчер: разбирает общие флаги, резолвит проект, зовёт подкоманду
src/lib/             paths · ui · detect · backends · journal · pricing
src/commands/        по файлу на команду
harness/             движок (см. ниже)
templates/           payload: что попадает в проект
meta/                что фабрика знает о проектах; в проект не копируется
memory/              pgvector + история; одна установка на все проекты
```

## Цикл (одна итерация)

```
┌─ harness/loop.ps1 ─────────────────────────────────────────────┐
│ 1. читает .bcf/STATE.md (итог прошлой итерации + backpressure) │
│ 2. один шаг агента в СВЕЖЕМ контексте                          │
│      команда из config/harness.json → agent.command,           │
│      промпт = PROMPT.md + STATE.md на stdin                    │
│ 3. backpressure: быстрая проверка + lint-gate + триггеры       │
│      провалы уходят в STATE.md для следующей итерации          │
│ 4. агент кладёт .bcf/VERIFY-REQUEST, когда код готов           │
│ 5. раннер зовёт harness/verify.ps1 (фазы C–E)                  │
│ 6. вердикт → tasks/.verdicts/<TASK>.md (в git, едет с задачей) │
│      PASS → остановка для ревью человеком                      │
└────────────────────────────────────────────────────────────────┘
```

Свежий контекст каждую итерацию — не оптимизация, а способ не дать контексту сгнить:
результат прошлой попытки приходит фактами (что упало, на какой строке), а не историей
диалога, в которой ошибка обрастает объяснениями.

**Предохранители:** таймаут итерации с убийством дерева процессов; сторож сети и
зависшего SSE-стрима; детект зацикливания (одна и та же ошибка ×N); детект отсутствия
прогресса (N итераций без изменений продуктового кода); потолок `MaxIterations`; файл
`.bcf/STOP`; долговечные git-снапшоты работы (`refs/bcf/wip/<task>`); идемпотентный гейт
(не гонять verify, когда ничего не менялось).

Агент проходит только фазы **0 → A.5 → A → B** (план, контракт, реализация,
самопроверка). Фазы **C → D → E** исполняет обвязка — никогда не агент.

## Верификация (harness/verify.ps1)

- **Фаза C — тестеры:** каждый LLM-тестер идёт изолированно, в свежем контексте, с диффом
  и скоупом задачи. Heartbeat, таймаут тишины, сбор осиротевших процессов.
- **Фаза D — визуальная** (опционально, `features.vision`): детерминированный контракт
  плюс LLM-критик по скриншотам.
- **Фаза J — сквозные сценарии** (`harness/journey-gate.ps1`): единственный гейт, который
  спрашивает про ПРОДУКТ, а не про дерево. Блокирующий, когда путь объявлен красным.
- **Фаза E — судья:** изолированный состязательный судья («PASS, только если не найду
  причины провалить»). **Совещательный.**
- **Вердикт детерминирован:** PASS ⟺ все гейты зелёные (проверки exit 0 + линт + визуальный
  контракт в скоупе + сквозные сценарии). Мнение судьи влияет на список remediation, а не
  на вердикт.
- **Вердикт называет, чем он получен:** строки `factory_version:` и `graph_hash:` стоят в
  его шапке и в итоге прогона (`.bcf/REVIEW.md`, `run-all.status.json`). Хэш считается по
  содержимому файла графа, а не по дате: граф правят чаще, чем версию, и «0.5.0» об этой
  правке не говорит ничего. Задача шла циклом, а не графом — так и написано, потому что
  пустая строка читается как «граф был, но не записался».

Обязательные проверки берутся из `config/checks.json` **проекта** и объединяются с планом,
который агент написал в `VERIFY-REQUEST`. Убрать их агент не может — это и закрывает дыру
«агент пишет себе план и получает тривиальный PASS».

### Почему Фаза J стоит отдельно от проверок задачи

Проверки задачи отвечают «её тест зелёный». Это правильный вопрос, и он ничего не говорит
о продукте. Прогон clinic-scheduler 2026-08-09 закрыл 35 задач из 35 и напечатал
«COMPLETE» ровно в тот момент, когда в приложении не работал ни один клиентский путь: у
оператора не было выбора даты, у регистратора кнопки оплаты и печати талона были
заглушками с подписью «недоступна», врач видел чужой день под сегодняшней датой. Ни один
гейт не соврал — `tsc` проверял типы, `eslint` стиль, а тесты экранов проверяли экран
против **мока собственного API**. Граница «экран ↔ сервер» не проверялась ничем, и все
дефекты оказались именно там.

Разрыв не в строгости проверок, а в том, на какой вопрос они отвечают. Сумма закрытых
задач не говорит о стыках между ними и об отсутствующих кусках. Поэтому:

- **у продукта есть собственное условие готовности** — `config/journeys.json`, реестр
  путей, ради которых он существует;
- **сценарий не мокает клиент API** — поднимает настоящий бэкенд и ходит в него живым
  запросом, а эффект проверяет запросом к серверу, а не состоянием интерфейса;
- **реестр содержит все пути с самого начала**; нереализованные помечены `planned` —
  названы вслух, слияние не блокируют и «готово» сказать не дают;
- **`run-all` печатает COMPLETE только когда** очередь закрыта, сценарии зелёные и P1
  приёмки нет. Любая другая комбинация получает статус, который нельзя прочитать как
  «продукт готов»;
- **красный сценарий на слитом дереве откатывает слияние** (`queue.graph.ps1`), а не
  превращается в строчку отчёта в конце прогона: строчку читают, когда всё уже слито.

Гейт доказан своими тестами: `pwsh harness/tests/journey-gate.tests.ps1` — девять случаев,
включая «тихий ноль» (раннер вернул 0 при нуле прогнанных тестов) и «часть путей зелёная,
остальные объявлены».

## Граф (harness/graph.ps1)

Граф — это обычный `.ps1` из `harness/graphs/`, устроенный так:

```powershell
$Meta = @{ name = '…'; description = '…'; phases = @(@{ title = '…'; detail = '…' }) }
if ($GraphMetaOnly) { return }
… тело: Set-Phase / Invoke-Node / Invoke-Pipeline / Invoke-Barrier …
```

Разделение на «мету» и «тело» нужно ровно для одного: показать состав фаз ДО того, как
что-то запустится. Прогон роя стоит денег, и решение «запускать ли» принимается по списку
фаз, а не по факту уже потраченного бюджета.

**queue** — очередь как граф. Волна это барьер, и он осознанный: готовность задачи зависит
от того, какие предшественники только что закрылись. Внутри волны барьеров нет — задача,
закончившая писать код, идёт сливаться, не дожидаясь соседок.

Два узла, которых у цикла нет вовсе:
- **арбитр слияния** — конфликт больше не равен «задача уходит человеку»: маркеры остаются
  в дереве, и их сводит отдельный агент. Прежний путь (`merge --abort`) стирал
  единственный контекст, по которому конфликт вообще разрешим;
- **разноракурсная приёмка** — несколько критиков на одном слитом дереве, у каждого свой
  угол. Одинаковые критики на одной модели дают согласованную чушь промышленного
  масштаба, поэтому ракурсы разные, а не количество больше. Состав и текст ракурсов —
  данные проекта, см. ниже.

**review** — поиск дефектов с состязательной проверкой. Три правила, без которых это не
работает: искатели смотрят разными глазами; проверяющих просят ОПРОВЕРГНУТЬ, а не
«оценить»; дедуп идёт по всему увиденному, включая отклонённое, иначе цикл не сходится.

**research** — один узел только на чтение, пишет ровно один файл.

### Ракурсы приёмки: чей вопрос, чьим текстом, каким весом

Ракурс — это запись в `config/review-lenses.json` плюс текст файлом в
`.claude/agents/critics/<id>.md`, рядом с тестерами. Оба графа читают их одной библиотекой
(`harness/lib/critics.ps1`): приёмка спрашивает про слитое дерево, ревью — про правку, а
сам вопрос, его вес и владелец у них общие.

```json
{ "id": "java", "owner": "лидер java", "blocking": true,
  "file": ".claude/agents/testers/java.md", "rules": 7 }
```

Разбор терпим к лишним полям: этот же файл пишет внешняя рассылка правил, и строгая схема
однажды выключила бы приёмку молча.

- **`owner`** — с кого спрашивать по находке этого ракурса. Пока владельца не было,
  находка приезжала «от критика», и адресовать её было некому. Владелец едет вместе с
  находкой в отчёт и в черновик задачи.
- **`blocking: true`** — провал ракурса роняет вердикт прогона. **`false`** — ракурс
  совещательный: находки печатаются отдельным разделом, вердикт не меняют. Пока веса не
  было, ракурс, заведённый «посмотреть», ронял прогон наравне с требованием заказчика, и
  такие ракурсы переставали заводить. Поле не указано — ракурс блокирующий: обратный
  дефолт снимал бы ракурс с вердикта из-за забытой строки.

Тексты кладёт в проект `bcf install` из `templates/claude/agents/critics/`. Файла в
проекте нет — движок берёт шаблон фабрики и **пишет об этом строку в журнал прогона**:
молчаливая подмена читается как «проект настроен под себя», и разбор чужой приёмки
начинается с поиска текста, которого в проекте нет.

Наборы по умолчанию у приёмки и ревью разные и это не небрежность. Приёмка смотрит на
слитое дерево (`invariants`, `seams`, `gates`, `journey`), ревью — на правку
(`correctness`, `failures`, `boundaries`, `gates`, `journey`). Общие два ракурса — честность
гейтов и работа пользователя: их ломают одинаково в обоих режимах.

Пока тексты лежали строками внутри `queue.graph.ps1`, поправить один вопрос можно было
только правкой движка, то есть сразу всем проектам. Приёмка чужого продукта шла ракурсами,
написанными под другой продукт: критик отвечал «указанные требования неприменимы» и сжигал
треть круга.

#### Приёмка, которой не было, называется вслух

У переезда текстов в проект есть обратная сторона: набор ракурсов может остаться совсем без
текста. Запись рассылки правил ссылается на файл тестера, которого в проекте нет, шаблона с
таким именем нет и в фабрике — ракурс пропускается, и спрашивать оказывается нечего. Раньше
этот случай выглядел как чистая приёмка: находок ноль, очередь закрыта, отчёт печатает
COMPLETE, а вопроса не задал никто.

Поэтому граф поднимает наверх два поля рядом с находками: `criticsExpected` (приёмка
ожидалась — в дерево что-то слито) и `criticsRun` (сколько ракурсов реально смотрело).
Ноль при ожидаемой приёмке даёт вердикт «ПРИЁМКА НЕ ВЫПОЛНЕНА», отчёт вместо COMPLETE
печатает «ОЧЕРЕДЬ ЗАКРЫТА, ПРИЁМКА НЕ ВЫПОЛНЯЛАСЬ», а в `run-all.status.json` появляется
`acceptance_skipped: true`. Это тот же сигнал, что у не ответившего критика, и разница
между ними названа: там спросили и не получили ответа, здесь не спросили никого.

### Номера требований заказчика

Задача называется «TASK-07 — карточка приёма» и ничего не говорит о том, какой пункт
договора закрывает. `harness/lib/requirement.ps1` читает номера из самой задачи: строка
`Требование: 3.1.1, ДКЦ1` в шапке или жирные номера в секции «## Требования». Их печатает
`bcf tasks` колонкой, а итог прогона — разделом «Требования заказчика», где пункт закрыт
только тогда, когда закрыты **все** назвавшие его задачи.

Зона чтения сужена намеренно: только шапка и только эта секция. Номер вида `3.1.1`
встречается в тексте задачи как версия пакета или пункт чек-листа, и разбор «где угодно в
теле» превратил бы колонку в мусор — задача с командой `npm view pkg@3.1.1` объявила бы
себя закрывающей требование 3.1.1.

### Владение файлами и допуск

git worktree изолирует деревья, но не предупреждает, что две ветки правят одни файлы:
конфликт всплывает на слиянии, когда оба агента уже приняли несовместимые решения.
Поэтому здесь не лок на время работы (долгие локи — известный провал: 20 агентов дают
пропускную способность 2–3), а **допуск на старте** плюс накопление фактов:

1. **заявка** `tasks/.claims/<TASK>.md` — кто взял задачу, в какой ветке, какие файлы
   объявлены и когда. Обычный файл в git, коммитится отдельным коммитом;
2. **co-change** — какие файлы исторически меняются вместе (по git log): декларация врёт,
   агент правит один файл, а ломает соседний, который его зовёт;
3. `conflicts.json` — какие пары задач реально сталкивались. Планировщик больше не сводит
   их в параллель, даже если декларации чисты.

Задача без секции «## Файлы» к работе не допускается: без декларации проверить, что она
не залезет в чужой файл, нечем, и расползание скоупа обнаружится только на слиянии.

### Шина команды — git

Фабрику ведут несколько человек с разных машин, и всё, что живёт в `.bcf/`, второй
участник не видит. Поэтому в git лежат две вещи, которые раньше были локальными.

**Вердикт** — файл `tasks/.verdicts/<TASK>.md`, и он больше не в `.gitignore`. Его пишет
обвязка в дерево задачи, он попадает в коммит ветки и приезжает в общую ветку тем же
слиянием, что и код. Пока он прятался, закрытая задача существовала ровно на одной машине:
второй участник видел бэклог, в котором не закрыто ничего, и его фабрика честно бралась
строить поверх несделанного. Вердикт незакрытой задачи, которую не слили, публикует
отдельным коммитом `Publish-TaskVerdict`.

**Заявка** — файл `tasks/.claims/<TASK>.md`. Живость считается по свежести записи, а не по
номеру процесса: pid чужой машины на своей либо не находится вовсе, либо принадлежит
постороннему процессу, так что «заявка жива» решалось угадыванием. Порог —
`team.claimTtlHours`, по умолчанию 12 часов; заявка старше задачу не держит, иначе
погасший ноутбук блокирует команду до утра. Второй претендент получает отказ с именем
первого и временем заявки, а не безымянное «пересечение файлов».
`.bcf/fleet/claims.json` остался локальным кэшем для сухого плана и экрана флота; спор
между кэшем и файлом решается в пользу файла.

### Откат слияния и правки человека

Красная проверка на слитом дереве откатывается `git revert` по общей ветке. Жёсткий сброс
на запомненный SHA допустим только внутри ветки задачи, где кроме неё никого нет. Прежний
`git reset --hard HEAD~1` снимал ПОСЛЕДНИЙ коммит, ничего не зная о том, чей он: между
слиянием и проверками проходят минуты, и в команде за это время в ту же ветку успевает
приехать чужая работа.

Правки в `tasks/` и `config/`, найденные в основном дереве во время прогона, уезжают
коммитом в ветку `bcf/parked/<дата>`. Раньше их отменял `git checkout --`: каталоги
принадлежат владельцу и в слиянии продуктового кода не участвуют, но пишет в них не только
узел ревизии плана, а ещё и человек, сидящий рядом. Его правка исчезала, а узнавал он об
этом из строки в логе ночного прогона. Забрать своё: `git checkout bcf/parked/<дата> -- <файл>`.

## Журнал и возобновление

Каждый узел графа пишется в `.bcf/graph/<runId>/journal.jsonl` — append-only и
единственный источник правды о прогоне. `bcf runs/board/report/cost` читают ОТСЮДА:
отдельная сводка рядом с журналом рано или поздно начинает с ним расходиться, и
расходится молча.

Оборванный прогон доигрывается: `--resume <runId>` берёт завершившиеся узлы из журнала и
не пересчитывает их.

Цикл ведёт свой журнал: `harness/lib/event-bus.ps1` пишет в `.bcf/events.jsonl`, состояние
(`.bcf/state/STATE.json`) — производная проекция, пересчитываемая из лога
(`harness/inspect.ps1 --replay`).

## Память (опционально, два независимых хранилища)

| | `memory/history` | `memory/pgvector` |
|---|---|---|
| Бэкенд | SQLite | Postgres 16 + pgvector (Docker) |
| Что хранит | история разработки (решения, провалы, ретро) | анти-паттерны агентов + реестр багов |
| Эмбеддинги | nomic-embed-text (768) | bge-m3 (1024) |
| Кто пишет | вручную / из вердиктов | ретроспектор, супервизор, узлы графа |
| Кто читает | `ask.py` | хук предзагрузки контекста, `Invoke-Node -Recall` |

Общего у них нет ничего. Оба деградируют мягко: без бэкенда эмбеддингов харнесс работает,
просто не учится.

**Что в цикле обучения ломалось раньше и как это чинится здесь.** Замер на прогоне из
14 задач: `anti_patterns = 1`, `bugs = 0`, `recall_events = 57` — механизм жил, но выучил
единственную заметку и потом 57 раз перечитывал её же. Две причины, обе молчаливые:
запрос собирался из строки-заглушки вместо реального текста узла, и писал уроки только
ретроспектор после вердикта, а вердиктов почти не было. Здесь отзыв идёт по настоящему
промпту узла, а пишут не только успехи: провал узла, провал задачи и подтверждённая
находка критика — все становятся уроками. Перед записью — дедуп по similarity: граф пишет
на порядок больше цикла, и без дедупа таблица за пару прогонов превращается в шум.

Всякий вызов памяти ограничен по времени. Без таймаута вспомогательная подсистема
превращается в жёсткую зависимость: наблюдалось живьём — Docker не был запущен, `recall`
висел на подключении, и прогон замер без единого события, снаружи выглядя как «граф
молчит».

## Роли

Роли — файлы `.claude/agents/*.md` в проекте: их читает и Claude Code как субагентов, и
обвязка при верификации. Одно место, а не два: вторая копия означала бы, что однажды
поправят не ту. Связь «роль → файл → модель» — в `config/agents.json`.

Три правила расстановки, за которые заплачено осознанно:

1. **critic не сидит на модели worker** — несколько агентов одной модели на одном
   контексте приходят к одной ошибке и подтверждают её друг другу;
2. **planner и critic из разных семейств** — критик не защищает решение собственного
   планировщика;
3. **кто только смотрит — живёт на песочнице «только чтение»**: иначе однажды что-нибудь
   поправит «по пути».

## Мета-слой

`meta/` знает о проектах, но в проекты не попадает. Реестр, append-only журналы аудита,
вики типичных ошибок, судьи со своим фикстурным харнессом.

Главное правило: кодовый агент не должен знать о существовании фабрики. Изоляция
обеспечивается рабочей директорией агента, а НЕ deny-правилом, называющим внешнюю папку —
само такое правило уже утечка. `bcf meta audit` считает найденную в проекте ссылку на
фабрику дефектом.
