# Установка

## Что нужно

| Что | Зачем | Оговорки |
|---|---|---|
| **Windows** | фабрика пока только под неё | Резолв bash для хуков (`Get-BcfBash`) и пути обвязки собираются через `\` по всему харнессу. `bcf doctor` на Linux/macOS отказывает сразу с этой причиной — слой путей ещё не переписан. |
| **PowerShell 7+** (`pwsh`) | движок и CLI | Windows PowerShell 5 не подходит: нет `$IsWindows`, автодополнения и части синтаксиса, на которые опирается харнесс. |
| **Git for Windows** | снапшоты работы, диффы, worktree, **и bash для хуков** | На PATH. Проект обязан быть репозиторием. `bash.exe` из Git for Windows — единственный bash, которым `bcf install` подставляет settings.json (WSL-лаунчер `bash` из PATH не годится, см. ниже). |
| **Кодовый CLI-агент** | собственно правки кода | Хотя бы один: `claude`, `opencode`, `codex`, `cursor-agent`. `bcf init` опросит установленные. |
| **Python 3.10+** | память (опционально), сканер секретов перед коммитом | Память — только при `features.memory` или `memory/history`. Сканер секретов (git-хук `.githooks/pre-commit`) без python не работает молча: любой коммит явно отказывает с этой причиной вместо того, чтобы пропустить его непроверенным. |
| **Docker** | pgvector (опционально) | Только для `memory/pgvector`. |
| **Сервер эмбеддингов** | векторная память (опционально) | LM Studio или любой OpenAI-совместимый `/v1/embeddings`. bge-m3 (1024) для pgvector, nomic-embed-text (768) для истории. |

## Установка фабрики

```bash
git clone <repo> bro-coding-factory
cd bro-coding-factory
```

Добавь `bin/` в PATH — или зови напрямую:

```bash
pwsh bin/bcf.ps1 --help          # Linux / macOS / Windows
bin\bcf.cmd --help               # Windows, cmd
```

Проверка, что фабрика на месте: `bcf --version` и `pwsh tests/cli.tests.ps1`.

## Настройка проекта

```bash
cd /path/to/your/project
bcf init
```

Восемь шагов, ни один токен не тратится, кроме живой пробы ролей. Что появится:

```
.claude/     хуки, скилы, команды, роли, settings.json
config/      harness.json, checks.json, agents.json, triggers.json, scope-map.json
tasks/       каркас бэклога + шаблон задачи
CLAUDE.md    заготовка правил проекта
.bcf/        состояние прогонов (добавляется в .gitignore)
```

После init обязательно посмотри две вещи, которые он назовёт сам:

1. **Список «без этого прогон не поедет».** Как правило это грязное дерево (первое же
   слияние затянет чужие правки в задачу) и падающая быстрая проверка (она вызывается
   каждую итерацию, и гейт будет красным всегда).
2. **`CLAUDE.md`.** Заготовка приходит с `TODO`. Пока он не заполнен, приёмке нечем
   обосновать блокировку, и ревью превращается в спор о вкусах.

Затем:

```bash
bcf doctor        # живая проба всех ролей — до того, как от них начнёт зависеть прогон
bcf tasks         # что в бэклоге, есть ли коллизии владения файлами
```

### Что придётся дописать руками

`bcf init` заполняет то, что можно вывести из файлов. Три вещи он вывести не может:

- **`config/harness.json` → `graph.roles.*.model`** — имя модели задаёт подписка, и
  общепринятого умолчания у большинства бэкендов нет.
- **`config/checks.json` → `_default`** — чем доказывается закрытая задача. Пустой
  `_default` означает, что задача без собственных проверок может получить PASS на одном
  судье.
- **`config/harness.json` → `tests.runner`** — если стек экзотический. Без него гейт
  «фича доказана тестами» не работает: общий прогон тестов зелен и на пустом месте.

### Bash для хуков

Claude Code исполняет `command` хука буквально, а голый `bash` на Windows чаще всего
находит лаунчер WSL (`C:\Windows\System32\bash.exe`), а не POSIX-оболочку репозитория:
на неинициализированном дистрибутиве первый же хук виснет на интерактивной настройке, а
без дистрибутива — падает молча. Поэтому `bcf install`/`bcf init` подставляют в
`.claude/settings.json` **полный путь** к настоящему Git Bash: сначала `git --exec-path`
(находит установку независимо от того, куда её положили), затем известные каталоги
(`Program Files\Git\...`), затем `PATH` без WSL-варианта.

Не нашли — `install` не пишет `settings.json` с голым `bash` (хуки в этом случае просто
не подключатся) и называет причину и что сделать: поставить Git for Windows либо задать
путь явно `$env:BCF_BASH = "C:\путь\к\bash.exe"`. Остальная обвязка (`hooks/`, `skills/`,
`config/`, `CLAUDE.md`) при этом всё равно ставится — довести настройку после установки
Git Bash: `bcf install --only claude`.

Подставленный путь в `settings.json` обёрнут в двойные кавычки
(`"{{BASH_PATH}}" .claude/hooks/...`): путь по умолчанию у Git for Windows —
`C:\Program Files\Git\bin\bash.exe`, пробел в `Program Files` без кавычек рвёт команду
на два токена, и её не находит ни `cmd.exe`, ни сам Git Bash.

### Секреты перед коммитом

Единственный сканер — git-хук `.githooks/pre-commit`. До 2026-09-06 сканером был
`.claude/hooks/secret-scan.sh` на `PreToolUse Bash`: он разбирал командную строку
`git commit`, чтобы угадать, что окажется в индексе. Разбор командной строки не закрыть
в принципе — `-a`/`-am`/`--all`, `git add && git commit` в одной строке, смена каталога
перед `add`, pathspec внутри самого `commit` (`-m msg <файл>`, `--include`, `--only`)
каждый раз были новым обходом, найденным следующим ревью (история пяти кругов — в
`docs/ROADMAP.md`, M-05). Смена подхода: сканер переехал в **настоящий git-хук**,
который git вызывает сам — уже ПОСЛЕ того, как разрешил любой способ стажирования.
Внутри хука `git diff --cached` — это ровно то дерево, что уедет в коммит, независимо
от того, каким путём git до него добрался. Разбирать командную строку больше незачем,
и обходить нечего: способ стажирования индекса хуку не важен.

**Установка.** `bcf install`/`bcf init` кладут файл шаблона в `.githooks/pre-commit`
проекта — обычный версионируемый файл, клонируется вместе с проектом — и включают его
командой `git config core.hooksPath .githooks`. Выбор в пользу `.githooks` +
`core.hooksPath`, а не копии в `.git/hooks/pre-commit`: `.git/hooks/` никогда не
клонируется (у второго участника команды `git clone` даёт пустой каталог хуков — правку
хука пришлось бы разносить вручную на каждой машине), а `.githooks/` — обычная папка
проекта, её содержимое видно сразу после клона. Сама активация (`core.hooksPath`) —
разовая локальная настройка, она в `.git/config` и не версионируется, но это тот же
класс настройки, что путь к `bash.exe` в `settings.json` выше: `bcf install` делает её
у каждого участника один раз, а обновления самого файла хука доезжают через обычный
`git pull`, без повторной установки.

Если у проекта уже есть свой `.git/hooks/pre-commit` или `core.hooksPath` указывает
на чужую систему хуков (Husky, python `pre-commit` framework, свой скрипт) — `install`
не перезаписывает и не дописывает вслепую: чужой хук может быть на любом языке, слепая
дозапись команды в конец чужого скрипта способна его сломать так, что заметят не сразу.
`.githooks/pre-commit` в этом случае всё равно ставится (файл доступен), но не
включается, и install печатает предупреждение с готовой строкой для ручной дозаписи —
предсказуемее и безопаснее, чем гадать, куда и как встроить вызов в чужой скрипт.

**Что ищет хук.** Признаки ключей доступа (AWS, Google Cloud, GitHub, Slack — по
образцам из `gitleaks`), PEM-блоков и присваиваний вида `password`/`api_key`/`token` с
непустым длинным значением-литералом — по добавленным строкам `git diff --cached -U0`.
Совпадение — коммит блокируется (`git commit` завершается ненулевым кодом), хук называет
файл и номер строки, само значение не печатается. Правило на присваивания — уже, чем в
`detect-secrets`: там ключевое слово принимает суффикс (`password_secure` тоже считается
находкой), здесь ключевое слово обязано стоять сразу перед оператором присваивания.
Иначе `password_default` из `config/memory.config.json` (несекретный локальный фолбэк,
см. выше) считался бы находкой при каждом коммите, задевающем этот файл. Значение-ссылка
на переменную окружения или конфиг (`process.env.*`, `os.environ`/`os.getenv`,
`System.getenv`, `config.*`, обращение к другой переменной вида `pwd = password`)
находкой тоже не считается: это код, который секрет уже читает из окружения, а не
хранит текстом.

Секрет, найденный в отслеживаемом файле, которого текущая команда не касается (не входит
ни в `-a`/`-am`, ни в pathspec, ни в реальный индекс), коммит не блокирует: `git diff
--cached` внутри хука показывает ровно то, что уйдёт в этот коммит, а не весь репозиторий.

Если коммит заблокирован, git сам откатывает любое стажирование, которое сделал ДЛЯ
ЭТОЙ команды (`-a`/`-am`/`--all`/pathspec/`--include`/`--only`) — файл возвращается в
состояние «изменён, не застейджен». Из реального индекса (застейджено отдельным `git
add` до этой команды) откат ничего не снимает — файл остаётся застейдженным. Текст
отказа называет обе возможности одной строкой, а не гадает, какая сработала: «убери
секрет из файла и закоммить заново; если после этого `git status` всё ещё показывает
путь застейдженным — `git restore --staged <файл>`».

Хуку самому нужен `python`/`python3` в PATH — без него `git diff` по образцам не
разобрать. Тихий пропуск здесь опаснее тихого пропуска где-либо ещё: гейт секретов
исчез бы незаметно на любой машине без python. Поэтому без python любой коммит
отказывает явно (причина называет отсутствующий python), а не проезжает непроверенным.

Выключить проверку: `BCF_SECRET_SCAN_DISABLED=1`, и только если в `docs/decisions.md`
проекта в тот же день есть запись `## <дата> ... BCF_SECRET_SCAN_DISABLED <причина>` —
тот же приём, что у остальных блокирующих хуков шаблона (`agent-infra-protect.sh`,
`done-gate.sh`, `dod-format-validator.sh`, `task-progression-gate.sh`). Без записи
коммит отказывает с этой же причиной.

**`.claude/hooks/secret-scan.sh` — тонкий предварительный вызов.** Тот же `PreToolUse
Bash`, что и `pre-bash-guard`, но секреты он не ищет сам: если команда похожа на `git
commit`, он напрямую вызывает `.githooks/pre-commit` по текущему индексу и, если тот
отказывает, возвращает Claude Code структурный `deny` (`hookSpecificOutput.
permissionDecision`, код 2, по доке `code.claude.com/docs/en/hooks`, сверено 2026-09-05)
ДО того, как git вообще запустится. Ловит только простой случай — секрет уже застейджен
отдельным `git add`, а сама команда commit индекс не меняет: тогда текущий `git diff
--cached` — это ровно то, что увидел бы настоящий git commit. Что именно считается
«простым случаем», решает не догадка по регэкспу, а разбор через `shlex` (тот же принцип
группировки кавычек, что у настоящего шелла): токены после `commit` должны укладываться
в короткий список безвредных флагов (`-m`/`--message`, `-q`, `-v`, `--allow-empty`,
`--no-edit`, `-e` и им подобные) плюс само сообщение — присутствие чего угодно ещё
(`-a`/`-am`/`--all`, `--include`, `--only`, любой pathspec-аргумент, `--` и файлы после
него) переводит команду в «сложный случай», и файл на ней молчит. Раньше здесь было
только обещание в комментарии, а код сканировал текущий индекс безусловно — ревью нашло
на этом ложный `deny`: секрет, застейдженный отдельно от файла в pathspec, блокировал
чистый `git commit -m сообщение -- doc.md`, хотя настоящий git эту же команду коммитит
(при частичном коммите git сам подставляет хуку временный индекс, ограниченный
pathspec — см. `git help commit`). «Сложный случай» этот файл теперь не проверяет и не
пытается угадать глубже — предсказать итоговый индекс, не исполняя команду, нельзя;
`.githooks/pre-commit` поймает такие коммиты сам в момент настоящего git commit (где
индекс уже настоящий), и Claude Code увидит обычную ошибку Bash-команды вместо
заблаговременного `deny`.

Отдельно от этого — файл денаит команду сразу, если в ней встретился `--no-verify`, `-n`
или `-c core.hooksPath=<что угодно>`. Это не разбор командной строки ради предсказания
индекса (тот класс задачи не закрыть в принципе, см. выше), а проверка присутствия
флага: `git commit --no-verify`/`-n` не даёт git вообще ВЫЗВАТЬ `.githooks/pre-commit`, а
чужой `-c core.hooksPath=` подменяет саму систему хуков на время команды — git-хук в
обоих случаях не может поймать свой собственный обход, и единственная точка, где это
вообще видно, — здесь, до запуска git. Проверка ловит и связку коротких флагов в одном
токене — `git commit -nm сообщение`, `git commit -anm сообщение` — единственная короткая
опция `git commit` с буквой «n» это сам `-n` (см. `git commit -h`), так что «n» до первой
«m» в связке (или без «m» вовсе) однозначно означает распакованный `-n`; ревью нашло, что
первая версия проверки сравнивала токен целиком с `-n` и связку пропускала. Текст
коммита, в котором слово `--no-verify` просто упомянуто внутри кавычек `-m` (например,
`git commit -m "отказ от --no-verify" файл.md`), флагом не считается: `shlex` видит это
как одно значение аргумента, а не отдельный токен. У этой проверки нет отдельного
выключателя — `BCF_SECRET_SCAN_DISABLED` (с записью в `docs/decisions.md`) остаётся
единственным официальным способом выключить сканер секретов.

**Остаточная граница.** `secret-scan.sh` — это `PreToolUse`-хук: он видит только команды,
которые Claude Code сам собирается выполнить через инструмент Bash. Человек, набравший
`git commit --no-verify` (или что угодно другое) в своём собственном терминале мимо
Claude Code, этим файлом не перехватывается в принципе — перехватить такую команду может
только `.githooks/pre-commit`, а `--no-verify` — это встроенное поведение git, которое
отключает вообще все хуки репозитория, не только наш. Держать в этом файле вторую,
самостоятельную логику разбора СОДЕРЖИМОГО коммита — значит вернуть тот самый класс
дефекта, который правка M-05a закрыла: единственный сканер секретов — файл git-хука,
`.claude/hooks/secret-scan.sh` его вызывает (и проверяет флаги-обходы), а не дублирует.
Известная непокрытая форма того же обхода: git сам принимает однозначное сокращение
длинной опции (`git commit --no-verif` работает как `--no-verify`, проверено живьём на
`git version 2.52.0`) — какая длина сокращения останется однозначной, зависит от полного
списка опций `git commit` этой версии git, и повторять здесь алгоритм git разрешения
сокращений — это тот же самый класс задачи «разбор командной строки ради предсказания»,
который правка M-05a закрыла в принципе. Полное написание `--no-verify` и связки с `-n`
ловятся; сокращённые длинные формы — нет.

## Векторная память

```bash
bcf memory init     # контейнер, схема, эмбеддинги, features.memory
bcf memory status   # счётчики: сколько уроков, багов, отзывов и сколько из них своих
```

Порт занят чужим контейнером — `init` подберёт свободный и запишет его в накладку этой
машины `.bcf/memory.local.json`. Это не педантизм: без подбора клиент подключился бы к
чужой базе, получил отказ авторизации, и выглядело бы это как поломка нашей памяти. В
отслеживаемый `config/memory.config.json` подобранный порт не пишется — он про машину,
а не про проект.

Схему `init` применяет сам. Контейнер выполняет `init.sql` только при первой
инициализации пустого каталога данных, поэтому базе, поднятой раньше, новые колонки
иначе не достанутся никогда — и запись начнёт падать «памятью недоступна».

База не на этой машине (`host` в конфиге не `localhost`) — контейнер не поднимается, а
пароль по умолчанию `init` не примет: он лежит в открытом репозитории. Задай настоящий
в `BCF_PG_PASSWORD`.

Одна база обслуживает все проекты машины, и каждая запись знает свой проект. Отзыв
спрашивает сначала свой проект и добирает чужое, только если своего не хватило: иначе
урок соседнего стека обходит свой по похожести и агент принимает его за свой.

Сервер эмбеддингов поднимается отдельно (например, LM Studio) — без него запись работает,
а отзыв нет, и снаружи это выглядит как «память пустая».

Проверка счётчиков после первого боевого прогона обязательна: если число уроков не
выросло, значит чтение работает, а запись — нет.

## Визуальная фаза

Требует визуального харнесса (снятие скриншотов → сравнение → агрегат) и дизайн-эталона.
Включать её без них — значит получить зелёный гейт на пустоте. Когда они есть:
`features.vision: true` плюс команды через окружение (`BCF_VISION_BUILD_CMD`,
`BCF_VISION_CONTRACT_CMD`, `BCF_VISION_CONTRACT_DIR`), см. [CONFIG.md](CONFIG.md).

## Ночные прогоны

```bash
bcf run night                    # вся очередь, автономно
bcf run night --max-iterations 30
```

Остановить между задачами — создать файл `.bcf/STOP`. Итог — `.bcf/REVIEW.md`,
машиночитаемо — `.bcf/run-all.status.json`, одним экраном — `bcf report`.

Для запуска по расписанию заверни `bcf run night` в cron или Планировщик задач Windows.
Прогон завершается ненулевым кодом, если очередь закрылась не вся, — на это можно
опираться в автоматизации.

## Несколько проектов

Одна установка фабрики обслуживает любое число репозиториев:

```bash
bcf doctor --project D:\projects\alpha
bcf run queue --project D:\projects\beta
```

Реестр и история аудита ведутся в фабрике: `bcf meta register`, `bcf meta list`.
