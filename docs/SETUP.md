# Установка

## Что нужно

| Что | Зачем | Оговорки |
|---|---|---|
| **Windows** | фабрика пока только под неё | Резолв bash для хуков (`Get-BcfBash`) и пути обвязки собираются через `\` по всему харнессу. `bcf doctor` на Linux/macOS отказывает сразу с этой причиной — слой путей ещё не переписан. |
| **PowerShell 7+** (`pwsh`) | движок и CLI | Windows PowerShell 5 не подходит: нет `$IsWindows`, автодополнения и части синтаксиса, на которые опирается харнесс. |
| **Git for Windows** | снапшоты работы, диффы, worktree, **и bash для хуков** | На PATH. Проект обязан быть репозиторием. `bash.exe` из Git for Windows — единственный bash, которым `bcf install` подставляет settings.json (WSL-лаунчер `bash` из PATH не годится, см. ниже). |
| **Кодовый CLI-агент** | собственно правки кода | Хотя бы один: `claude`, `opencode`, `codex`, `cursor-agent`. `bcf init` опросит установленные. |
| **Python 3.10+** | память (опционально), сканер секретов перед коммитом | Память — только при `features.memory` или `memory/history`. Сканер секретов (`secret-scan.sh`) без python не работает молча: на команде, похожей на `git commit`, он явно отказывает с этой причиной вместо того, чтобы пропустить коммит непроверенным; на остальных командах не вмешивается. |
| **Docker** | pgvector (опционально) | Только для `memory/pgvector`. |
| **Сервер эмбеддингов** | векторная память (опционально) | LM Studio или любой OpenAI-совместимый `/v1/embeddings`. bge-m3 (1024) для pgvector, nomic-embed-text (768) для истории. |

## Установка фабрики

```bash
git clone <repo> bro-coding-factory
cd bro-coding-factory
```

Добавь `bin/` в PATH — или зови напрямую:

```bash
pwsh bin/bcf.ps1 --help          # Linux / macOS / Windows
bin\bcf.cmd --help               # Windows, cmd
```

Проверка, что фабрика на месте: `bcf --version` и `pwsh tests/cli.tests.ps1`.

## Настройка проекта

```bash
cd /path/to/your/project
bcf init
```

Восемь шагов, ни один токен не тратится, кроме живой пробы ролей. Что появится:

```
.claude/     хуки, скилы, команды, роли, settings.json
config/      harness.json, checks.json, agents.json, triggers.json, scope-map.json
tasks/       каркас бэклога + шаблон задачи
CLAUDE.md    заготовка правил проекта
.bcf/        состояние прогонов (добавляется в .gitignore)
```

После init обязательно посмотри две вещи, которые он назовёт сам:

1. **Список «без этого прогон не поедет».** Как правило это грязное дерево (первое же
   слияние затянет чужие правки в задачу) и падающая быстрая проверка (она вызывается
   каждую итерацию, и гейт будет красным всегда).
2. **`CLAUDE.md`.** Заготовка приходит с `TODO`. Пока он не заполнен, приёмке нечем
   обосновать блокировку, и ревью превращается в спор о вкусах.

Затем:

```bash
bcf doctor        # живая проба всех ролей — до того, как от них начнёт зависеть прогон
bcf tasks         # что в бэклоге, есть ли коллизии владения файлами
```

### Что придётся дописать руками

`bcf init` заполняет то, что можно вывести из файлов. Три вещи он вывести не может:

- **`config/harness.json` → `graph.roles.*.model`** — имя модели задаёт подписка, и
  общепринятого умолчания у большинства бэкендов нет.
- **`config/checks.json` → `_default`** — чем доказывается закрытая задача. Пустой
  `_default` означает, что задача без собственных проверок может получить PASS на одном
  судье.
- **`config/harness.json` → `tests.runner`** — если стек экзотический. Без него гейт
  «фича доказана тестами» не работает: общий прогон тестов зелен и на пустом месте.

### Bash для хуков

Claude Code исполняет `command` хука буквально, а голый `bash` на Windows чаще всего
находит лаунчер WSL (`C:\Windows\System32\bash.exe`), а не POSIX-оболочку репозитория:
на неинициализированном дистрибутиве первый же хук виснет на интерактивной настройке, а
без дистрибутива — падает молча. Поэтому `bcf install`/`bcf init` подставляют в
`.claude/settings.json` **полный путь** к настоящему Git Bash: сначала `git --exec-path`
(находит установку независимо от того, куда её положили), затем известные каталоги
(`Program Files\Git\...`), затем `PATH` без WSL-варианта.

Не нашли — `install` не пишет `settings.json` с голым `bash` (хуки в этом случае просто
не подключатся) и называет причину и что сделать: поставить Git for Windows либо задать
путь явно `$env:BCF_BASH = "C:\путь\к\bash.exe"`. Остальная обвязка (`hooks/`, `skills/`,
`config/`, `CLAUDE.md`) при этом всё равно ставится — довести настройку после установки
Git Bash: `bcf install --only claude`.

Подставленный путь в `settings.json` обёрнут в двойные кавычки
(`"{{BASH_PATH}}" .claude/hooks/...`): путь по умолчанию у Git for Windows —
`C:\Program Files\Git\bin\bash.exe`, пробел в `Program Files` без кавычек рвёт команду
на два токена, и её не находит ни `cmd.exe`, ни сам Git Bash.

### Секреты перед коммитом

`.claude/hooks/secret-scan.sh` встаёт на тот же `PreToolUse Bash`, что и `pre-bash-guard`:
перед `git commit` сканирует staged-дифф (`git diff --cached`) на признаки ключей доступа
(AWS, Google Cloud, GitHub, Slack — по образцам из `gitleaks`), PEM-блоков и присваиваний
вида `password`/`api_key`/`token` с непустым длинным значением-литералом. Совпадение —
коммит блокируется, хук называет файл и номер строки, само значение не печатается.
Правило на присваивания — уже, чем в `detect-secrets`: там ключевое слово принимает
суффикс (`password_secure` тоже считается находкой), здесь ключевое слово обязано стоять
сразу перед оператором присваивания. Иначе `password_default` из
`config/memory.config.json` (несекретный локальный фолбэк, см. выше) считался бы находкой
при каждом коммите, задевающем этот файл. Значение-ссылка на переменную окружения или
конфиг (`process.env.*`, `os.environ`/`os.getenv`, `System.getenv`, `config.*`, обращение
к другой переменной вида `pwd = password`) находкой тоже не считается: это код, который
секрет уже читает из окружения, а не хранит текстом.

`git commit -a`/`-am`/`--all` стажирует отслеживаемые правки внутри самого коммита, уже
после проверки индекса — при этих флагах хук дополнительно сканирует весь `git diff`
(рабочее дерево без `--cached`), иначе секрет, лежащий в правке без `git add`, проезжал
бы мимо на пустом `--cached`. При `git add ... && git commit ...` в одной команде логика
похожая, но дифф не берётся весь репозиторий: хук — `PreToolUse`, он видит команду и
индекс до её исполнения, поэтому `git add` из той же строки ещё не сработал в момент
проверки. Аргументы сегмента `add` отдаются настоящему `git add --dry-run` (git сам
разворачивает `-A`/`.`/glob и учитывает `.gitignore`) — и дифф рабочего дерева
ограничивается ИМЕННО этими путями (`git diff -- <пути из --dry-run>`), а не всем
рабочим деревом. Файл, который команда не добавляет и не коммитит, в проверку не
попадает, даже если в нём лежит секрет: раньше (найдено пятым ревью M-05) хук сканировал
весь `git diff` при любом `git add`, и локальная правка `password = "..."` в отслеживаемом,
но не добавляемом файле блокировала чужой, чистый коммит. Неотслеживаемые новые файлы из
ответа `--dry-run` сканируются целиком по содержимому, отдельно от diff-парсера.

Текст отказа даёт разный совет в зависимости от того, где находка: секрет, уже лежащий в
индексе (застейджен отдельным `git add` до этой команды), снимается `git restore
--staged <файл>`. Секрет из рабочего дерева — из `-a`/`-am`/`--all` или из `git add`
той же командной строки — этой командой ещё не индексирован, `git restore --staged`
там ничего не отменяет; совет для него другой: убрать секрет из файла или не включать
этот путь в `add`/`-a`/`-am` и закоммитить остальное отдельно.

**Граница защиты.** Хук — `PreToolUse`, он смотрит на команду и на диск ДО её
исполнения. Файл, который команда создаёт сама в той же строке, — например,
`echo секрет > c.txt && git add c.txt && git commit` — на момент проверки ещё не
существует: хук его не видит и не сканирует, а после исполнения команды секрет уже
закоммичен. Это не обходной путь, найденный кем-то нарочно, а сама природа проверки
до выполнения — единственная защита от такого случая, это не создавать секрет и
коммит одной командной строкой.

Ответ хука для `PreToolUse` — по доке `code.claude.com/docs/en/hooks` (сверено
2026-09-05): `hookSpecificOutput.permissionDecision: "deny"` вместо верхнеуровневого
`decision`, блокировка держится на коде возврата 2, который блокирует независимо от
того, разобран ли JSON.

Ту же связку `cd <каталог> && git add ... && git commit ...` хук тоже видит: `git add
--dry-run` в этом случае запускается из каталога, куда перевёл предыдущий `cd` в той же
командной строке (git печатает путь относительно корня репозитория независимо от этого),
а не всегда из корня — иначе pathspec, данный относительно подкаталога, не совпадал бы
ни с чем. Список неотслеживаемых файлов и ответ `git add --dry-run` сравниваются с
`core.quotepath=false`: без этого `git ls-files` C-квотирует не-ASCII имя файла иначе,
чем печатает `git add --dry-run`, и файл с таким именем (например, кириллицей) выпадал
бы из сравнения и не сканировался вовсе.

Хуку самому нужен `python`/`python3` в PATH — без него JSON от Claude Code не разобрать.
Тихий пропуск здесь опаснее тихого пропуска где-либо ещё: гейт секретов, зарегистрированный
в `settings.json`, исчез бы незаметно на любой машине без python. Поэтому на команде,
похожей на `git commit`, хук без python отказывает явно (код 2, причина называет
отсутствующий python), а не пропускает коммит непроверенным; на прочих командах не
вмешивается, чтобы не заблокировать вообще весь Bash в проекте.

## Векторная память

```bash
bcf memory init     # контейнер, схема, эмбеддинги, features.memory
bcf memory status   # счётчики: сколько уроков, багов, отзывов и сколько из них своих
```

Порт занят чужим контейнером — `init` подберёт свободный и запишет его в накладку этой
машины `.bcf/memory.local.json`. Это не педантизм: без подбора клиент подключился бы к
чужой базе, получил отказ авторизации, и выглядело бы это как поломка нашей памяти. В
отслеживаемый `config/memory.config.json` подобранный порт не пишется — он про машину,
а не про проект.

Схему `init` применяет сам. Контейнер выполняет `init.sql` только при первой
инициализации пустого каталога данных, поэтому базе, поднятой раньше, новые колонки
иначе не достанутся никогда — и запись начнёт падать «памятью недоступна».

База не на этой машине (`host` в конфиге не `localhost`) — контейнер не поднимается, а
пароль по умолчанию `init` не примет: он лежит в открытом репозитории. Задай настоящий
в `BCF_PG_PASSWORD`.

Одна база обслуживает все проекты машины, и каждая запись знает свой проект. Отзыв
спрашивает сначала свой проект и добирает чужое, только если своего не хватило: иначе
урок соседнего стека обходит свой по похожести и агент принимает его за свой.

Сервер эмбеддингов поднимается отдельно (например, LM Studio) — без него запись работает,
а отзыв нет, и снаружи это выглядит как «память пустая».

Проверка счётчиков после первого боевого прогона обязательна: если число уроков не
выросло, значит чтение работает, а запись — нет.

## Визуальная фаза

Требует визуального харнесса (снятие скриншотов → сравнение → агрегат) и дизайн-эталона.
Включать её без них — значит получить зелёный гейт на пустоте. Когда они есть:
`features.vision: true` плюс команды через окружение (`BCF_VISION_BUILD_CMD`,
`BCF_VISION_CONTRACT_CMD`, `BCF_VISION_CONTRACT_DIR`), см. [CONFIG.md](CONFIG.md).

## Ночные прогоны

```bash
bcf run night                    # вся очередь, автономно
bcf run night --max-iterations 30
```

Остановить между задачами — создать файл `.bcf/STOP`. Итог — `.bcf/REVIEW.md`,
машиночитаемо — `.bcf/run-all.status.json`, одним экраном — `bcf report`.

Для запуска по расписанию заверни `bcf run night` в cron или Планировщик задач Windows.
Прогон завершается ненулевым кодом, если очередь закрылась не вся, — на это можно
опираться в автоматизации.

## Несколько проектов

Одна установка фабрики обслуживает любое число репозиториев:

```bash
bcf doctor --project D:\projects\alpha
bcf run queue --project D:\projects\beta
```

Реестр и история аудита ведутся в фабрике: `bcf meta register`, `bcf meta list`.
