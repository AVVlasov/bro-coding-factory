# bcf — справочник команд

> Это справочник: что делает каждая команда и почему именно так. Если нужен порядок
> действий — «что запускать за чем и что означает то, что я вижу» — смотри
> [WORKFLOW.md](WORKFLOW.md).

## Как это зовут

```bash
pwsh bin/bcf.ps1 setup     # один раз — добавляет bin/ в PATH
# новое окно
cd D:\projects\my-app
bcf                        # состояние и выбор запуска
bcf run queue              # проект берётся из текущего каталога
```

`--project` нужен только тогда, когда работаешь над чужим каталогом, не выходя из своего:
`bcf doctor --project D:\projects\other`. В обычной работе его не пишут.

## bcf (без аргументов)

Карточка состояния и выбор запуска. Шесть строк — шесть вещей, отсутствие которых
обнаруживается на прогоне, а не до него: бэклог, состояние последнего прогона, бэкенды с
ролями, память (ЧИСЛАМИ, не «ок»), дата тарифов, подписки. Строка, для которой данных нет,
печатается со словом «нет» и ценой этого — не прячется и не выдумывается.

Строка **прогон** отвечает на вопрос, ради которого карточку и открывают: идёт ли что-то
прямо сейчас, оборвалось ли ночью, или последний прогон закрылся с провалами. Состояние
берётся из журнала, а не из файла-маркера: маркер переживает падение процесса и потом
сутками уверяет, что работа идёт. Рядом с каждым состоянием стоит команда, которая ему
соответствует — `bcf watch`, `bcf runs`, `bcf log --failed`, `bcf report`.

Дальше — выбор: `↑↓` курсор, `space` отметить задачу, `a` все, `d` только готовые,
`enter` запустить, `p` сухой план, `q` выход. Отметки передаются графу входом: экран,
чьи галочки ни на что не влияют, выглядит управлением, а является украшением.

Смета считается **по прошлым прогонам этого проекта**, а не по прайсу «в среднем»: сколько
стоит узел, знают только журналы. Нет истории — так и написано.

Без консоли (пайп, CI, планировщик) экран уступает место печати: то же состояние плюс
список команд, код возврата 0.

`bcf --screen` рисует один кадр выбора и выходит — этим он покрыт тестами.

## bcf setup

```
bcf setup           добавить bin/ в PATH пользователя
bcf setup --check   только проверить
bcf setup --remove  убрать
```

На Windows правит PATH пользователя (HKCU), не системный: системный требует прав
администратора и трогает всех. На Linux/macOS печатает строку для профиля оболочки, но не
правит его сам — это чужой файл.

---

Общие флаги есть у всех команд:

| флаг | что делает |
|------|------------|
| `--project <путь>` | над каким проектом работать. По умолчанию — верх git-репозитория текущего каталога |
| `--yes` | не задавать вопросов: берётся значение по умолчанию, и каждое такое умолчание называется вслух |
| `--no-color` | вывод без цвета |

Корень проекта резолвится один раз, в диспетчере, и передаётся дальше через
`BCF_PROJECT_ROOT` — подкоманды и весь харнесс читают одну и ту же величину, разъехаться
им негде.

---

`bcf setup` делает три вещи, и каждая — про то, чтобы инструментом можно было
пользоваться, а не вспоминать его:

- **PATH пользователя** (HKCU, не системный: правка системного требует прав администратора
  и трогает всех, кому эта фабрика не нужна);
- **ярлык `BCF` в меню «Пуск»** — `pwsh -NoLogo -NoExit -Command bcf` с рабочим каталогом
  фабрики. Без него CLI существует только для того, кто уже сидит в консоли с открытым
  нужным каталогом. `--no-shortcut` — не создавать;
- **автодополнение** команд и подкоманд, дописанное в профиль пользователя (живёт между
  сессиями, работает в новых окнах).

`--remove` снимает и путь, и ярлык. `--check` не меняет ничего.

## bcf init

Настройка фабрики под проект. Восемь шагов, каждый заканчивается текстовым файлом.

```
bcf init            интерактивно
bcf init --yes      без вопросов
bcf init --dry      показать решения, ничего не записав
```

1. **Где проект** — git ли это, чисто ли дерево, была ли инициализация раньше.
2. **Разбор проекта** — языки, сборка, `productPaths`, `backpressure`, `generatedFiles`,
   раннер тестов. Кандидаты в быструю проверку **запускаются живьём**: «скрипт прописан»
   и «скрипт отрабатывает» — разные утверждения, и харнесс ломает второе.
3. **Кодовые агенты** — опрос установленных CLI, авторизации проверяются по-настоящему.
4. **Роли графа** — planner / worker / arbiter / critic. Узлы считаются **по настоящей
   очереди** из `tasks/`, а не по примеру: сколько задач допущено к работе, сколько будет
   волн, зовётся ли планировщик (он нужен только при коллизии владения) и сколько ракурсов
   у приёмки — последнее читается из самого графа, поэтому не разъедется с ним. Коллизии
   владения и задачи без секции «Файлы» называются здесь же: развести их руками дешевле,
   чем платить планировщику за то же решение.
5. **Модели на роли** — выбирается ЯРУС, а не цена: рамочных решений мало и они дорогие,
   исполнения много и оно дешёвое.
6. **Источники замысла** — README, CLAUDE.md, PRD.
7. **Бэклог** — каркас `tasks/` и шаблон задачи. Нарезку init не делает: он не зовёт
   агентов и не выдумывает задачи за владельца.
8. **Запись** — что легло на диск и что осталось сделать руками.

Ручная работа в конце разделена на **«без этого прогон не поедет»** и **«можно позже»**.
Один общий список из восьми пунктов человек не разбирает, он его закрывает.

Цены на этих шагах не показываются намеренно: init настраивает, а не продаёт. Смета —
`bcf cost`.

**init заполняет пустое, а не переписывает заполненное.** Проект мог настраиваться руками
или прошлой версией фабрики, и там уже стоят выверенные бэкенды с моделями — включая те,
которые init угадать не может (имя модели задаёт подписка). Всё, что было заполнено,
остаётся и перечисляется в разделе «оставлено как было». Заменить своими догадками —
`bcf init --reconfigure`.

Недостающие секции конфига (`tests`, `backpressure`, `graph`) при этом ДОБАВЛЯЮТСЯ: конфиг
проекта бывает старше фабрики.

## bcf install

```
bcf install                поставить недостающее
bcf install --force        перезаписать (правки в этих файлах будут потеряны)
bcf install --dry          показать, что было бы записано
bcf install --only claude  только .claude
```

По умолчанию **ничего не перезаписывается**. Обвязка — это файлы, которые владелец правит
под себя; молчаливая перезапись при обновлении фабрики теряет его правки, а замечает он
это на следующем прогоне.

`.claude/settings.json` получает **полный путь** к `bash.exe`, а не голое имя команды:
голый `bash` на Windows чаще ловит лаунчер WSL, а не Git Bash (подробности — `bcf doctor`
ниже). Настоящий bash не нашёлся — `install` не пишет `settings.json` вовсе (остальная
обвязка всё равно ставится) и заканчивается кодом `2` с причиной и что сделать
(`$env:BCF_BASH` или установить Git for Windows).

## bcf migrate

```
bcf migrate --dry      показать план
bcf migrate            перенести
bcf migrate --copy     скопировать, старое оставить
```

Нужна проектам, которые водили харнесс до перехода на `.bcf/`: их история лежит в
`loop/.graph`, `loop/.fleet`, `loop/retros` и так далее. Читать её `bcf` умеет и без
переноса (иначе он говорил бы «прогонов ещё не было» при полусотне сохранённых
журналов), но ПИШЕТ только в `.bcf/` — и пока история разделена, список склеивается из
двух источников.

Останавливается, если одно и то же есть в обоих каталогах: слить две истории
автоматически нельзя, а выбрать «которая новее» за тебя — значит однажды выбрать не ту.

Скрипты старого харнесса (`loop/*.ps1`) не трогает: движок теперь в фабрике, а их копия
в проекте не мешает.

## bcf detect

Разбор проекта, не пишет ничего. `--probe` дополнительно запускает кандидатов в
`backpressure`, `--json` отдаёт машиночитаемо.

## bcf doctor

```
bcf doctor              бэкенды + память + проверки
bcf doctor --no-probe   без запросов к моделям
bcf doctor --checks     ещё и прогнать backpressure проекта
```

Единственное место, где doctor тратит токены, — по одному короткому запросу на роль.
Он нужен потому, что **дефекты проводки молчаливы**: неавторизованный бэкенд отвечает
штатным событием, а не падением, и снаружи это неотличимо от пустого ответа модели.

Про память doctor печатает ЧИСЛА, а не «ок»: память бывает доступна и при этом содержать
один урок, который перечитывается полсотни раз.

Фабрика пока целиком под Windows: резолв bash (`Get-BcfBash`) и пути обвязки собираются
через `\`. На Linux/macOS `doctor` отказывает сразу, не пытаясь изобразить живую пробу —
слой путей под них ещё не переписан.

Коды возврата: `0` — готов (возможно с оговорками), `1` — есть блокирующее (в том числе
«не Windows»).

## bcf tasks

Состояние очереди плюс то, что считается детерминированно и потому не стоит ни токена:

- **готовность** — все ли предшественники имеют `verdict: PASS`;
- **коллизии владения** — две задачи на одном файле без предшествования. Планировщик
  пустит обе в одну волну, и арбитр будет сводить два независимых переписывания: это
  ярус слияния, дороже и рискованнее прогона по очереди;
- **задачи без секции «Файлы»** — их допуск не работает вовсе;
- **задачи у людей** — те, у кого в файле стоит `Исполнитель: <имя>`. Они видны в таблице
  отдельным состоянием «у человека» с именем в колонке «исполнитель», но фабрика на них
  агента не запускает и в число «готово к работе» они не входят.

## bcf task

```
bcf task new "<название>"              создать файл задачи по шаблону
bcf task new "<название>" --for Иван   то же, но задачу ведёт человек
bcf task why <ID>                      почему эта задача не может пойти в работу
bcf task show <ID>                     файл задачи, её вердикт и разведка одним экраном
```

`new` берёт **следующий свободный** номер, а не «количество файлов + 1»: после удаления
задачи второе выдаёт занятый id, и два файла начинают спорить за один вердикт. Имя файла
транслитерируется — кириллица в пути ломает часть инструментов, которые харнесс зовёт
снаружи, а имя задачи попадает в команды буквально. Строка предшественников кладётся сразу
в том формате, который читает движок, чтобы не выяснять, какой из двух «правильный».

`--for <имя>` проставляет в файле задачи строку `Исполнитель: <имя>`. Задачу с таким полем
фабрика не берёт: её нет ни в очереди `bcf run night`, ни в волнах `bcf run queue`, и в
журнале прогона про неё сказано «пропущена: исполнитель <имя>». В `bcf tasks` она остаётся
видна с состоянием «у человека». Раньше того же добивались строкой `**Gate-вход:** TASK-00`,
и задача попадала в отчёт как заблокированная, то есть выглядела сломанной, а не занятой.
Вернуть её фабрике — стереть строку или написать в ней «фабрика». Поле можно поставить и
руками — в шапке задачи, между заголовком `# TASK-NN` и первой секцией `## `. Ниже первой
секции его не читает никто: ни фабрика, ни разборщики пула, — а строка `Исполнитель:`
внутри примера команд в «## Проверки» иначе отправляла бы задачу человеку.

`why` отвечает на вопрос, который идёт следом за «ждёт TASK-02» в списке задач: **почему**
именно. Проверяет по порядку — незакрытые предшественники (и отдельно те, у которых нет
даже файла: такой гейт не закроется никогда), декларацию владения файлами, коллизии с
задачами без предшествования, наличие обязательных проверок в `config/checks.json` и
заполненность ролей графа. Код возврата `1`, если задача не поедет.

## bcf run

```
bcf run loop <TASK>    цикл по одной задаче
bcf run night          цикл по всей очереди, автономно
bcf run queue          граф: волны по зависимостям
bcf run review         граф: разноракурсная приёмка по слитому дереву
```

| флаг | |
|------|---|
| `--dry-plan` | показать план, не запуская ни одного агента |
| `--budget <токены>` | потолок на прогон (граф) |
| `--concurrency <N>` | сколько узлов/задач одновременно |
| `--resume <runId>` | доиграть оборванный прогон: готовые узлы берутся из журнала |
| `--max-iterations N` | потолок итераций на задачу (цикл) |

Остановить ночной прогон — `bcf stop` (см. ниже).

Прогон отказывается стартовать, если не заполнено то, что ему нужно: роли и бэкенды для
графа, `agent.command` для цикла. Проверяется именно ЭТО, а не факт прохождения `bcf init` —
проект с уже настроенным `config/harness.json` работает и без мастера.

`--dry-plan` не создаёт НИЧЕГО: ни рабочих деревьев, ни заявок на файлы. Он пишет только
свой журнал, помеченный как сухой, — чтобы прогон было видно в `bcf runs`.

### Живой экран прогона

В консоли `bcf run queue` и `bcf run review` рисуют экран из макета — **лента сверху,
прибитая доска снизу**:

- **лента** — события, а не лог. Служебный префикс `[graph]` выброшен (он повторяется в
  каждой строке и не несёт ничего), время приглушено, волна выделена, слияние зелёным,
  провал красным, `[memory]` идёт отдельной темой. Scrollback живой — ленту можно
  отмотать.
- **доска** перерисовывается на месте: шапка (граф, runId, время, агентов, токенов),
  конвейер фаз со стрелками, полоса с процентом, кто работает прямо сейчас с ролью,
  моделью, временем и токенами, провалы с причинами, последние готовые, статус-бар.

**Оценка «осталось»** считается по фактическим длительностям узлов ЭТОГО прогона. Меньше
двух закрытых узлов — оценки нет вовсе: выдуманное «осталось 6 минут» решает за человека,
ждать ему или гасить.

Про работающий узел показывается то, что действительно известно: роль, модель, время,
токены и **пульс** (`214с, тишина 3с`). Чем именно занят агент в эту секунду, он не
сообщает, и правдоподобная выдумка здесь хуже отсутствующей строки.

Подтверждение запуска спрашивает САМ CLI: вывод движка перенаправлен, и его собственный
вопрос ушёл бы в перенаправленный поток — прогон встал бы молча, ожидая ответа, которого
никто не видит.

Без консоли (пайп, CI, планировщик) — честный проброс сырого лога движка: перерисовка на
месте превратилась бы в кашу из управляющих последовательностей, а лог нужен именно
сырым. Следить за чужим прогоном из другого окна — `bcf watch`.

## Как экраны договариваются об итоге

`bcf run`, `bcf report`, `bcf board`, `bcf watch` и карточка `bcf` берут вердикт из одного
места — из того, **что вернул сам граф** (поле `result` события `run-finish`), а не из
числа отработавших узлов. Правило вынесено в одну функцию (`Get-BcfRunComplete`), потому
что оно неочевидное и его легко потерять: узлы могут отработать все до одного, а очередь
остаться незакрытой — узел «работа-TASK-01» честно завершается и тогда, когда задача не
достигла PASS.

Пока правило жило только в `bcf report`, наблюдалось следующее на одном и том же прогоне:
сам прогон печатал зелёное «итог: ок» и возвращал код 0, доска показывала «завершён» и
100%, карточка — зелёную галочку, а отчёт — «НЕПОЛНО, закрыто 0 из 1». Из четырёх экранов
три врали, и все три — в сторону успеха; ночной запуск по расписанию записывал в историю
успех там, где не было сделано ничего.

Неполный прогон даёт код возврата **1** — и у `bcf run`, и у `bcf report`.

## bcf runs · board · report

- `bcf runs` — журналы прошлых прогонов графа. Состояния различаются: **сухой план**
  (агентов не звали), **ОБОРВАН** (можно доиграть), **неполно** (граф доиграл, очередь
  закрылась не вся), **ок**.
- `bcf board [runId]` — узлы по фазам с ролями, временем и токенами; причина провала
  печатается рядом с узлом, а не отдельным разделом внизу.
- `bcf report [runId]` — итог одним экраном. Слово «готово» звучит ТОЛЬКО при полностью
  закрытой очереди; вердикт берётся из того, что вернул сам граф, а не из числа
  отработавших узлов. Неполный прогон даёт код возврата 1.

## bcf log

```
bcf log                     узлы последнего прогона: где что сохранилось
bcf log <часть имени узла>  ответ этого узла, его ошибки, его промпт
bcf log --failed            только упавшие
bcf log <runId> <узел>      то же по конкретному прогону
bcf log <узел> --prompt     с каким промптом узел звали
bcf log <узел> --raw        поток бэкенда как есть, без разбора
```

Доска и отчёт отвечают «что случилось». Следующий вопрос всегда один: **а что он вообще
ответил**. Промпт, поток ответа и stderr пишутся на каждый узел и так — команда не заводит
ничего нового, она делает уже существующее доступным, не заставляя угадывать имя файла.

У упавшего узла первым печатается **stderr бэкенда**: ответа там обычно нет, а причина
есть. Пустой файл ответа не выдаётся за сохранённый ответ — именно так выглядит молча
умерший агент, и списку нельзя обещать то, чего в нём нет.

Текст достаётся из потока событий по всем известным схемам сразу — задача показать ответ,
а не разобрать протокол. Что не разобралось, названо неразобранным, с подсказкой про
`--raw`.

## bcf stop

```
bcf stop           попросить остановиться между задачами
bcf stop --now     снять работающие процессы агентов
bcf stop --clear   убрать запрос на остановку
```

Разница между режимами существенная. **Мягкий**: прогон дочитает текущую задачу и
остановится сам — итерация доводится до конца, вердикт пишется, рабочее дерево убирается.
**`--now`**: текущая итерация теряется целиком, рабочее дерево остаётся заклеймлённым, и
следующая волна не возьмёт те же файлы, пока заявка не снята. Это аварийный тормоз, а не
«побыстрее».

`--now` ставит файл-запрос **тоже**: оркестратор, переживший снятие дочерних процессов,
иначе спокойно возьмёт следующую задачу — и остановка будет выглядеть несработавшей.

Перед тем как что-то сделать, команда говорит, было ли что останавливать: идёт ли прогон,
какой, и сколько процессов проекта видно.

## bcf watch

```
bcf watch           следить за идущим прогоном
bcf watch <runId>   доска конкретного прогона
bcf watch --once    один кадр и выход
```

Читает **журнал, а не процесс**. Поэтому работает и для прогона, запущенного в другом окне
или по расписанию, и после его конца, и одновременно в трёх окнах — новой точки состояния
не заводится.

Прогон считается идущим, если журнал дописывался меньше 90 секунд назад. Отдельного
признака «идёт» нет намеренно: файл-маркер переживает падение процесса и врёт до
следующей уборки. У оборванного прогона незавершённые узлы показываются как **«не
завершились»** с временем до последней записи в журнал — растущий таймер там означал бы,
что работа идёт, когда процесса давно нет.

Когда стартует новый прогон, доска перескакивает на него сама. Выход — `q`; прогон
продолжается.

## bcf cost

```
bcf cost              последний прогон
bcf cost <runId>      конкретный
bcf cost --all        все
bcf cost --json       машиночитаемо
```

Тарифы берутся из `config/pricing.json` проекта или `memory/pricing.json` фабрики; вместе
с суммой печатается их ДАТА, потому что прайсы меняются, а файл — нет.

Для модели без тарифа стоимость показывается прочерком, а не нулём: ноль в колонке денег
читается как «бесплатно». Узлы, отработавшие с нулевым расходом, называются отдельно —
их бэкенд не сообщает токены, и бюджетный ограничитель на такой роли слеп.

Формат `pricing.json` — цена за 1M токенов:

```json
{ "updated": "2026-07-31", "currency": "USD", "rate": 1.0,
  "models": { "opus": { "input": 15, "output": 75 } } }
```

## bcf memory

```
bcf memory status      что в памяти лежит и растёт ли это
bcf memory init        поднять pgvector, проверить эмбеддинги, включить в конфиге
bcf memory ask <текст> что память помнит по этому поводу
bcf memory down        остановить контейнер (данные остаются)
```

`init` отказывается стартовать, если порт занят чужим контейнером: иначе клиент
подключится к чужой базе, получит отказ авторизации, и выглядеть это будет как поломка
нашей памяти.

`status` печатает счётчики и прирост за неделю. Отсутствие прироста — это не «всё в
порядке», а «читаем старое и не учимся на свежем».

Про Docker команда спрашивает **канал демона**, а не `docker version`. Разница не
косметическая: на Windows `docker version` при незапущенном Docker Desktop не падает — он
его ЗАПУСКАЕТ и ждёт готовности. Наблюдалось: прогон висел больше шести минут, не
напечатав ни строки, поднял Docker Desktop на машине и вывесил поверх всего его диалог об
ошибке. Проба по каналу отвечает за десятки миллисекунд и ничего не запускает; сам Docker
Desktop команда не поднимает и говорит об этом прямо.

Прогон уважает `features.memory` из `config/harness.json`. Пока не уважал, обычный проект
(флаг выключен по умолчанию) получал поднятый контейнер pgvector и строку «цикл обучения
АКТИВЕН» — при том, что его собственная карточка писала «память выключена».

## Что делает CLI, когда внешняя команда молчит

Правило одно: **у любого внешнего вызова есть потолок времени, и ход долгой работы видно.**
Молчащая пять минут команда неотличима от зависшей — её убивают ровно перед тем, как она
бы закончила.

- `docker` зовётся через обёртку с потолком; stderr **возвращается**, а не выбрасывается,
  иначе вызывающий печатает свой выдуманный диагноз («не поднялся за 45с») вместо
  настоящего («нет доступа к реестру»).
- Долгие операции (`compose up`, загрузка образа ~450 МБ) идут потоком: строки видно по
  мере появления, и отдельно сказано, что образа нет локально и это минуты.
- Таймаут пробы **не** сходит за ответ. «docker не ответил за 15с» — это своё состояние, а
  не «контейнера нет»: иначе подвисший демон отправляет восстановление поднимать
  контейнер, о котором ничего не известно, то есть потолок времени становится входом в
  новое зависание.
- `lms load` (модель эмбеддингов, гигабайты с диска) запускается отдельным процессом, а
  ожидание — по часам, с отметками «всё ещё гружу» каждые полминуты.
- Аргументы с пробелами закавычиваются. Без этого `--format '{{.Names}} {{.Status}}'`
  уезжает двумя аргументами, `docker` падает на разборе за доли секунды, и снаружи это
  неотличимо от «демон не ответил».
- `bash` под Windows берётся не из PATH: первым там стоит лаунчер WSL, который на
  неинициализированном дистрибутиве уходит в интерактивную настройку и блокируется на
  stdin. Порядок (`Get-BcfBash`): `BCF_BASH` → `git --exec-path` (Git for Windows, любое
  место установки) → известные каталоги (`Program Files\Git\...`) → любой bash из PATH,
  кроме лаунчера WSL. Не нашёлся нигде — `bcf install`/`bcf init` не пишут `settings.json`
  с голым `bash`, см. `bcf install` выше.

## bcf research \<TASK\>

Разведка задачи до работы: что уже есть, чего не хватает для проверяемой готовности, и
какие развилки обязан решить человек. Пишет ровно один файл `tasks/<TASK>.research.md`.

Роль живёт на песочнице «только чтение», если такая есть; если нет — команда об этом
предупреждает: роль, обязанная лишь смотреть, однажды что-нибудь поправит «по пути», и
правка приедет в задачу как чужая.

`--apply` дополнительно вписывает ссылку на разведку в файл задачи. Без флага файл задачи
не трогается: задача — контракт.

## bcf prd

Четыре вопроса, закрывающие развилки, которые агент не имеет права решать сам: кто
пользователь и что для него «работает»; что входит в MVP; чего в первой версии НЕ делаем;
чем доказывается закрытая задача.

Под `--yes` записывается ЗАГОТОВКА с вопросами, а не выдуманные ответы — и об этом прямо
говорится. Четвёртый ответ обязан доехать до `config/checks.json`: иначе он остаётся
пожеланием, а общие проверки зелены и на пустом месте.

## bcf meta

```
bcf meta list                реестр: где проекты и когда их последний раз смотрели
bcf meta register            занести текущий проект
bcf meta audit               проверить обвязку текущего проекта
bcf meta wiki [запрос]       лучшие практики и типичные ошибки
bcf meta log "<что сделали>" запись в append-only журнал аудита
```

Слой существует потому, что **обвязка деградирует молча**: хук, переставший срабатывать
после обновления CLI, не сообщает об этом — он просто перестаёт блокировать, и проект
ещё месяцами выглядит защищённым.

`audit` отдельно проверяет, что в проекте НЕТ ссылок на фабрику: кодовый агент не должен
знать о её существовании, и сама такая ссылка — утечка, после которой он туда идёт.
Изоляция обеспечивается рабочей директорией, а не deny-правилом, называющим внешнюю папку.

## bcf update

```
bcf update            подтянуть новую версию и показать, что изменилось
bcf update --check    только посмотреть, есть ли новее
bcf update --to <ref> перейти на конкретную версию или ветку
```

Отличается от `git pull` тремя вещами, и каждая — про то, что обновление инструмента,
который водит чужие проекты, не должно ничего сломать молча:

1. **Локальные правки.** Фабрику правят под себя — это её нормальный режим. Обновление
   останавливается на грязном дереве, а не перезаписывает чужую работу.
2. **Что изменилось для тебя.** Не список коммитов, а ответ на «что теперь делать»:
   поменялись ли *шаблоны* (обвязку в проектах стоит освежить — `bcf install --dry`
   покажет дифф), *схема конфига* (новые ключи в существующих проектах сами не появятся),
   *движок* (поведение прогона другое, подхватится сразу — движок один на все проекты) или
   только сам CLI (проекты трогать не нужно).
3. **Откат.** Версия до обновления называется явно, одной командой.

После слияния идёт самопроверка: на месте ли обязательные файлы и разбирается ли каждый
`.ps1`. Битую фабрику надо увидеть здесь, а не на ночном прогоне.

Слияние только быстрой перемоткой. Если поверх есть свои коммиты — команда останавливается
и предлагает слить руками: конфликт в инструменте такого рода смотрят глазами.
