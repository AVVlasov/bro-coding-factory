# Сервис умирает целиком от emit('error') без слушателя — а симптом выглядит как «фича упала»

**Дата:** 2026-06-12 · **Проект-источник:** samantha-backend · **Класс:** надёжность node-сервисов

## Симптом

Пользовательская фича «не работает» (research в «Профессиях» падает / UI «не отвечает»),
хотя её код корректен. На самом деле **умер весь backend-процесс**: в логе
`ERR_UNHANDLED_ERROR`, порт перестал слушаться. Фоновый node умирает молча (известная
грабля), поэтому атрибуция уезжает в последнюю видимую фичу.

## Корень

В Node `EventEmitter.emit('error')` **без подписчика бросает** (специальное поведение
события `error`) и валит процесс. Ловушка собирается из двух невинных решений:

1. Клиент шлюза (`openclaw/client.ts`) транслирует события ядра как `emit('error', …)`.
2. Подписчик (`chat-bridge`) слушает `error` **только пока стримит ответ чата** —
   подписка временная, по дизайну.

Событие же приходит **и вне активного чата**: gateway шлёт `chat state:'error'`
(«LLM request timed out») для чужих ранов — research-сессий, cron-дайджестов, каналов.
Первый же стопор LLM-стрима в фоновом ране = мёртвый сервис.

## Фикс (паттерн)

`emitErrorSafe`: эмитить `error` только при живых подписчиках, иначе — warn-лог:

```ts
private emitErrorSafe(err: Error): void {
  if (this.listenerCount('error') > 0) this.emit('error', err);
  else log.warn('gateway error (no listener)', { message: err.message });
}
```

- регрессионный тест: «error-событие без подписчика не убивает процесс; с подписчиком доходит».

## Чему учит при аудите

- Ищи `emit('error'` в долгоживущих клиентах/мостах: если подписка на `error`
  не **постоянная**, это бомба замедленного действия.
- «Фича X нестабильна» при однопроцессном backend — сначала проверь, жив ли процесс
  и что в его stderr, а не код фичи (см. также
  [[verification-gate-lies-and-loop-grind]] про ложную атрибуцию).
- Любое событие из внешней шины (gateway/ws) может прийти в момент, когда «по дизайну»
  его никто не ждёт — контракты подписок проверять на полном жизненном цикле, не на
  happy path чата.

## Смежные WSL/OpenClaw ground-truth грабли (samantha, 2026-06-13)

- **`wsl.exe` рвёт большой контент в argv → ENAMETOOLONG.** Провижининг файла в дистро через
  `bash -lc "echo <base64> | base64 -d > файл"` ломается, когда контент крупный (PROFESSIONS.md
  ~22.5КБ, двойной base64 в argv превышает лимит длины командной строки). Фикс: контент через
  **stdin**, не через argv (`provisionFileAt` в distro.ts). То же касается кавычек/многострочности
  — единственный надёжный транспорт в дистро — base64-скрипт + stdin.
- **`openclaw agents delete --force` (сборка 2026.6.5) НЕ прунит каталог `workspace-<id>/`.**
  Агент уходит из реестра и из allowlist, но его воркспейс-директория остаётся на диске.
  Формулировка help «prunes workspace/state» оптимистична. При каскадном удалении профессии
  директории чистить явным `rm -rf`, иначе копятся осиротевшие воркспейсы.
- **`WorkspaceVanishedError` при повторном `agents add` после ручной чистки воркспейса.**
  Ядро хранит аттестацию воркспейса в `workspace-attestations/<sha256(абсолютный путь)>.attested`.
  `agents delete --force` снимает её сам, но если воркспейс-директорию снесли `rm -rf` ВРУЧНУЮ
  (см. предыдущий пункт), аттестация остаётся осиротевшей → следующий `agents add` на тот же
  путь падает `WorkspaceVanishedError`. Лечение: удалить осиротевший файл аттестации точечно —
  имя файла = `sha256(путь воркспейса)` (хэш фигурирует и в тексте ошибки). НЕ чистить чужие
  аттестации (по mtime отличить свои от предсуществующих).

## Процесс-грабля: «голый» фоновый агент умирает в простое

Тяжёлый background-Agent на многочасовой задаче может тихо умереть, если сессия простаивает
(пример: агент B-14 встал на ночь ~11ч на самом финише — код написал, но не догнал тесты и
не закрыл статус; выглядело как «задача в работе», а реально ничего не крутилось). Для долгих
задач — **journaled Workflow** (переживает перерыв, возобновляем по runId), не raw Agent.
Диагностика смерти: mtime лога агента не двигается + нет изменений целевых файлов + порт
стенда свободен. Восстановление: запустить доводчика, который СНАЧАЛА оценивает уже написанное
(build/test), а не переделывает с нуля.
