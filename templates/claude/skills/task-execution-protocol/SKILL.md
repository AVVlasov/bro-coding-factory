# Task Execution Protocol

Поведенческий гайд для исполнения задач из `tasks/`. Полная версия с обоснованием —
[`docs/agentic/task-execution-protocol.md`](../../../docs/agentic/task-execution-protocol.md).
Активируется на старте и закрытии любой задачи.

> **Зачем.** 2026-05-16 кодовый агент дважды закрыл STACK-задачи с ложными `[V]`:
> HIGH-баг, неустранённая гонка, отсутствующие тесты. Причина — пропуск исследования
> и верификации. Этот скил делает пропуск невозможным.

## Фаза 0 — Исследование (ДО написания кода)

Правка кода стартует только после прохождения Фазы 0.

1. **Прочитать целиком** все файлы из секции «Файлы» задачи + смежный код, который они
   вызывают/импортируют. Понять текущее поведение фактически — `grep`, чтение, запуск.
   Не угадывать. Не хватает знаний — вызвать скил `/deep-research`.
2. **Найти граничные режимы** до кода: ветки `if`, режимы запуска (`startMinimized`,
   `isTestMode`, `autoStart`), пустые/ошибочные состояния. Каждый DoD-assertion должен
   держаться **во всех** релевантных ветках, а не только на happy-path.
3. **Декомпозиция** — вызвать скил `/vertical-slice-decomposition`. Шире одного owner,
   >7 assertions, или всплыла смежная работа → §«Subtask-делегация».
4. Зафиксировать план: что меняем, какие режимы затронуты, чем проверяется каждый assertion.

## Subtask-делегация

Дробить обязательно, если истинно хоть одно: задача требует второго owner-типа;
нашлась смежная проблема вне DoD; assertion невозможно закрыть без отдельного крупного куска.

**Как:** создать `tasks/STACK-NN.<seq>-<slug>.md` (формат — `false-completion-defense.md`
§11.11), в parent проставить `[X] → subtask: tasks/STACK-NN.<seq>-<slug>.md`, подзадачу
отдать профильному субагенту через `Agent` tool:

| Слой подзадачи | Субагент |
|----------------|----------|
| Процессы, службы, жизненный цикл приложения | профильный агент слоя из `.claude/agents/` |
| React / страницы / компоненты | `react-ui-developer` |
| FastAPI / Python | `python-backend-developer` |
| Миграции БД | `db-migration-writer` |
| Адаптеры внешних сервисов / транспорт | профильный агент слоя из `.claude/agents/` |
| Навигация по коду «где это» | `codebase-explorer` |

Не делать чужой слой «по-быстрому» одним проходом — это путь к багам.

## Фазы A..E

- **A — Реализация** по §2 задачи (vertical slice: IPC закрывается тремя местами разом).
- **B — Самопроверка:** `tsc --noEmit` / `pytest` — прочитать exit code; для UI — поднять
  0 ошибок в консоли приложения. Скил `/self-verification`.
- **C — Тестеры:** `/verify STACK-NN` → `architecture` (всегда) + `api` /
  `db-migration-writer` / `performance` по затронутым слоям.
- **D — Визуальная проверка:** UI-задача → `/red-team`, vision `total ≥ 40` в 4 темах,
  0 CRITICAL. Не-UI → зафиксировать «UI не затронут».
- **E — Судья:** `judge` видит DoD + diff + все отчёты → вердикт.

## Доказательный гейт — устное «выполнено» не считается

Задача STACK-NN закрыта **только** когда сошлись три места:
1. чекбоксы `[V]` в §5 task-файла — после реальной верификации;
2. `tasks/.verdicts/STACK-NN.md` с `verdict: PASS` и свежим `diff_fingerprint`
   (`git diff HEAD | git hash-object --stdin`) — пишет `/verify` после судьи;
3. `tasks/CURRENT-FOCUS.md` — фокус переводится на следующую задачу только после этого.

Хуки стерегут это принудительно:
- `done-gate.sh` блокирует `Stop`, если judge-assertion `[V]` без свежего PASS-вердикта;
- `task-progression-gate.sh` блокирует перевод `CURRENT-FOCUS` на задачу, чей `Gate-вход`
  предшественник не имеет PASS-вердикта.

Отчёт «выполнено» в чате без verdict-файла — это «работа продолжается», не «сделано».
`NEEDS-MORE-EVIDENCE` и `FAIL` закрытием не являются.

**Лексика отчёта.** «Выполнено» / «done» / «задача закрыта» — только при `verdict: PASS`
в `tasks/.verdicts/STACK-NN.md`. Без вердикта пиши: **«код готов, не верифицирован —
нужны Фазы C–E»**. Заголовок «STACK-NN — выполнено» при непройденных тестерах/судье —
ложный отчёт, даже если ниже в теле признано «тестеры не запускались».

## Анти-паттерны (авто-стоп — вернуть assertion в `[ ]`/`[~]`)

- Проставить `[V]` без `/verify` и без verdict-файла.
- `[V]` на assertion, верный лишь в одном режиме (happy-path), при наличии других веток.
- «Реализация в файле есть» = `[V]` без проверки живости пути во всех режимах.
- «Не проверяемо в этой сессии» вместо запуска теста, который проект уже умеет запускать.
- Закрыть задачу с ненаписанным обязательным тестом из DoD.
- Пропустить Фазу 0 и начать с правок кода.
- Списать упавший тест / сломанный harness на «pre-existing infrastructure issue» без
  проверки `git diff HEAD` — не внёс ли регрессию ты сам (инцидент 2026-05-17).

## Порядок закрытия задачи (обязательный)

`Фаза 0..D` → `/verify STACK-NN` (фаза E) → verdict-файл записан → проставить `[V]` →
`done-gate` пропускает `Stop` → обновить `CURRENT-FOCUS` на следующую задачу.

## Контракт отчёта (после каждого блока работы)

Закончив фазу или осмысленный блок работы — выдать отчёт Andrey **строго по форме**
ниже и **остановиться**. Отчёт всегда **на русском**.

```
## Отчёт — STACK-NN

**Цель:** <одна строка — что задача должна дать в итоге>

**Ограничения и предпочтения:** <ключевые ограничения: charter, read-only, стек>

**Статус:** код готов, не верифицирован — нужны Фазы C–E
            ИЛИ задача закрыта — verdict: PASS (только если verdict-файл реально есть)

**Прогресс:**
- Сделано: <реально сделанное — файл:строки, что именно>
- В работе: <начатое, но не законченное — что сделано / что осталось>
- Заблокировано: <что и чем блокировано; «нет», если ничего>

**Проверено (чем):**
- npx tsc --noEmit → exit 0
- <тест / grep / прогон + фактический результат>
- НЕ проверено: <честно — тестеры, судья, verdict-файл, незакрытые assertions>

**Ключевые решения:** <неочевидные выборы; зафиксированы ли в docs/decisions.md>

**Следующие шаги:**
1. <конкретный шаг — команда / файл / действие>
2. <конкретный шаг>

**Критический контекст:** <подводные камни, неудавшиеся попытки, что важно знать дальше>

**Затронутые файлы:** <список изменённых/созданных файлов>

**Жду «продолжай».**
```

**Правила контракта:**
- После отчёта — **СТОП**. Не начинать следующую фазу или задачу, пока Andrey не
  написал «продолжай» (или не дал правки). Andrey контролирует результат вручную.
- В «Сделано» — только реально сделанное. Незавершённое → «В работе», непроверенное →
  «НЕ проверено». Не выдавать намерение за факт.
- «Статус» = «выполнено / задача закрыта» — только при `verdict: PASS` (см. «Лексика отчёта»).
  Иначе — «код готов, не верифицирован».
- «Следующие шаги» — всегда конкретны (команда / файл / действие), не «доделать задачу».
- Отчёт целиком — на русском.
