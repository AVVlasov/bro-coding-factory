# /feature

Превращает «сделай Х» в задачу, у которой есть владелец-файлы и проверяемая готовность.
Без этого шага задача формулируется в момент реализации, и первая же приёмка спорит с
исполнителем о том, что вообще требовалось.

## Порядок

1. **Границы.** Прочитай `docs/PRD.md` (если есть) и убедись, что фича внутри MVP. Если
   она за границей — скажи об этом и остановись: расширение области — решение владельца
   продукта, а не агента.

2. **Владение файлами.** Выпиши файлы, которые придётся править. Правило: **один файл —
   один владелец**. Если файл уже закреплён за другой активной задачей (`tasks/*.md`,
   секция «Файлы»), это коллизия — назови её и предложи либо предшествование, либо
   передачу файла. Две задачи, независимо переписывающие один файл, сводятся арбитром,
   и это дороже последовательного прогона.

3. **Готовность.** Сформулируй не больше трёх условий, каждое — проверяемое КОМАНДОЙ, а
   не взглядом. «UI работает» условием не является. «`<команда теста>` даёт ≥3 прошедших
   теста по фильтру `<модуль>`» — является. Команду бери из `config/harness.json` →
   `tests`.

4. **Файл задачи.** Создай `tasks/<PREFIX>-<NN>-<slug>.md` (префикс — `taskIdPrefix` из
   конфига) с секциями:

   ```
   ## Файлы        — что задача имеет право править
   ## Готовность   — до трёх проверяемых условий
   ## Проверки     — конкретные команды, которые это доказывают
   ## Вход         — задачи-предшественники, если есть
   ```

5. **Обязательные проверки.** Допиши команды из «Проверки» в `config/checks.json` под
   ключом задачи. Это единственное место, где проверки задаёт НЕ агент, — и потому
   единственное, что он не может сузить до тривиального PASS.

## Чего не делать

- Не начинать правку кода в этом же ходе. `/feature` заканчивается файлом задачи.
- Не писать больше одной связной фичи в задачу: то, что нельзя закрыть одним PASS,
  будет крутиться в цикле, пока не упрётся в потолок итераций.
