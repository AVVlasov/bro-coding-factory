# /review

Ревью правок по правилам ЭТОГО проекта, а не по общим представлениям о хорошем коде.

## Откуда берутся правила

1. `CLAUDE.md` — то, что владелец записал явно. Это главный источник; если нарушено —
   это блокер, а не замечание.
2. `config/harness.json` → `productPaths` — что вообще считается продуктовым кодом.
   Правки вне этих путей в ревью не участвуют.
3. `.claude/hooks/hooks-config.json` — архитектурные запреты, которые проект уже
   формализовал (границы слоёв, запрещённые импорты, миграции).

Правило, которого нет ни в одном из трёх источников, — это твоё мнение. Его можно
высказать, но пометив как мнение, а не как нарушение.

## Что смотреть

Диапазон: `git diff HEAD --` (или `git diff --cached`, если есть staged). Если задан
`$ARGUMENTS` — ограничься этим префиксом.

По каждому изменённому файлу проверь, в порядке убывания цены ошибки:

1. **Корректность.** Краевые значения, гонки, порядок операций. Находка обязана иметь
   КОНКРЕТНЫЙ вход, дающий неверный выход. Без него это не находка.
2. **Отказы.** Проглоченное исключение, пустой `catch`, тихий фолбэк на дефолт,
   непроверенный внешний ответ, ресурс без освобождения на пути ошибки.
3. **Границы.** Слой полез в чужой слой; изменение сломало существующих вызывающих;
   формат ошибки поменялся молча.
4. **Честность тестов.** Ассерт на константу, замокан ровно тот объект, который и
   проверяется, тест без ассертов. Такой тест хуже отсутствующего: он даёт зелёный гейт.

## Формат вывода

```
БЛОКЕРЫ      — нарушают CLAUDE.md или ломают поведение. Каждый: файл:строка, что
               сломается, на каком входе.
ЗАМЕЧАНИЯ    — стоит поправить, но не блокирует.
МНЕНИЕ       — вкусовое, правил не нарушает.
```

Пустой раздел печатается как «(нет)». Не растягивай ревью: три настоящих блокера ценнее
двадцати замечаний, среди которых они утонут.
